# 思维推理链 Tick 循环机制实现方案

> 日期：2026-10-28
> 状态：方案（除已标注「本轮已完成」的对话入口清理外，未改动运行时代码）
> 范围：`subsystem/lunar_harness/lunar`（Tick 调度、对话接入）、`engine/mood`（心情）、`engine/life`（生活体系）、`agents/BilibiliViewer`（观影执行器）、`agents/MutualForum`（论坛执行器）、`engine/memory`（记忆整理）
> 目标：把每秒 Tick 从「对话链 + 观影特例」升级为「单占用、按优先级、可注册扩展」的统一调度器，并补齐心情、生活事件、记忆整理三条配套机制。

---

## 0. 结论摘要

本方案做四件事：

1. **统一 Tick 调度器**：每秒一个 Tick，同一时刻只允许一个体系运行；按「运行中跳过 → 未读消息 → 待处理视频切片 → 生活冷却到期 → 空闲计数」的顺序判定，所有触发/释放都经过同一把锁。
2. **生活体系**：把生活事件做成可注册、可恢复的状态机；按权重与每日额度选择事件，额度耗尽兜底「发呆」；事件按原子步骤执行，每步返回后立即释放 Tick，未完成的事件在下一空闲 Tick 续跑。
3. **心情子系统**：启动时计算 5 种基础情绪嵌入，维护多维心情向量；只允许生活体系更新；把心情标签、近期生活记录、未来一小时计划写进对话者运行时消息。
4. **记忆整理事件**：全量文本记忆分批（每批 ≤ 1 万字符、单条不截断），调用 `primary_reasoning` 去重/合并/筛选/润色，删除旧批次并写入新记忆；用批次意图日志保证崩溃后可恢复。

**关键取舍（本方案明确下来的部分）：**

| 议题 | 结论 | 理由 |
|---|---|---|
| 事件执行粒度 | 一个事件由多个原子步骤组成，每步一次模型/工具调用，返回即释放 Tick | 避免「整理记忆」这类长事件把对话锁死几分钟；同时满足「拿到工具结果后释放」 |
| 生活事件与观影体系的关系 | 生活事件「刷视频」只负责**启动**一轮哔哩观影；启动产生的待处理切片交给观影体系按中优先级逐片执行 | 复用现有 `BilibiliViewer` 的 Tick 状态机，不把长观看流程塞进生活事件 |
| 对话者与哔哩观影 | 移除对话者的 `network_explore.bilibil_viewer` 入口及其快速应答 | 用户明确要求；哔哩观影归属生活体系 |
| 计划表判定 | 从对话 Tick 移除，只在生活体系运行时统一判定 | 按需求迁移；905 秒冷却小于 30 分钟计划宽限，正常不会丢计划 |
| 状态持久化 | 调度器、生活、心情各自独立状态文件，统一原子写 | 职责清晰，重启可恢复，避免一个大文件互相拖累 |

## 2. 术语与总体架构

### 2.1 三个体系

| 体系 | 职责 | 触发条件 | 执行粒度 |
|---|---|---|---|
| 对话体系（thinking） | 消费未读消息、跑完一轮对话 | `UnreadCount() > 0` | 一轮对话（可能跨多次模型调用） |
| 观影体系（viewing） | 执行 `BilibiliViewer` 已启动任务的切片步骤 | `BilibiliViewer.HasPendingWork()` | 一个切片/合并/发布步骤 |
| 生活体系（life） | 选择并执行生活事件；维护心情、生活记录、计划摘要 | 有未完成事件，或空闲 Tick ≥ 905 | 一个事件原子步骤 |

优先级固定为：**对话 > 观影 > 生活**。新增体系通过注册接口插入，不改主调度逻辑。

### 2.2 分层

## 3. 核心 Tick 调度器

### 3.1 类型定义（放入 `lunar/type.go`）

```go
// TickSnapshot 一次 Tick 判定所需的只读快照。
type TickSnapshot struct {
	Now            time.Time
	IdleTicks      int
	Unread         int
	ViewingPending bool
}

// TickSystem 可注册的 Tick 体系。
// 新增体系只需实现该接口并 Register，主调度逻辑不改。
type TickSystem interface {
	ID() string
	Priority() int
	// Ready 返回本 Tick 是否应运行，以及可读的触发原因（日志/验收用）。
	Ready(TickSnapshot) (bool, string)
	// Run 执行一个原子工作单元；返回即表示释放 Tick。
	Run(ctx context.Context) error
}

// TickState 调度器持久化状态。
type TickState struct {
	Version        int    `json:"version"`
	IdleTicks      int    `json:"idle_ticks"`
	LastSystem     string `json:"last_system"`
	LastReason     string `json:"last_reason"`
	LastTriggerAt  int64  `json:"last_trigger_at"`
	UpdatedAt      int64  `json:"updated_at"`
}
```

### 3.2 调度器实现（`lunar/tick_scheduler.go`）

```go
type tickScheduler struct {
	mu      sync.Mutex
	systems []TickSystem // 按 Priority 降序
	state   TickState
	busy    bool
	ctx     context.Context
	cancel  context.CancelFunc
	wg      sync.WaitGroup
	tickSeq int64
}

func (s *tickScheduler) Register(sys TickSystem) {
	s.mu.Lock()
	defer s.mu.Unlock()
	for _, item := range s.systems {
		if item.ID() == sys.ID() {
			logger.Warn(tickModule, "[Tick] 体系 %s 重复注册，已忽略", sys.ID())
			return
		}
	}
	s.systems = append(s.systems, sys)
	sort.SliceStable(s.systems, func(i, j int) bool {
		return s.systems[i].Priority() > s.systems[j].Priority()
	})
}

func (s *tickScheduler) Tick() {
	s.mu.Lock()
	if s.busy { // 规则 1：运行中直接跳过，不计数
		s.mu.Unlock()
		return
	}
	snap := TickSnapshot{
		Now:            time.Now(),
		IdleTicks:      s.state.IdleTicks,
		Unread:         UnreadCount(),
		ViewingPending: BilibiliViewer.HasPendingWork(),
	}
	for _, sys := range s.systems {
		ready, reason := sys.Ready(snap)
		if !ready {
			continue
		}
		s.busy = true
		s.state.IdleTicks = 0          // 规则 3/4/5：任一体系触发即清零
		s.state.LastSystem = sys.ID()
		s.state.LastReason = reason
		s.state.LastTriggerAt = snap.Now.Unix()
		s.tickSeq++
		seq := s.tickSeq
		s.persistLocked()
		s.mu.Unlock()
		logger.Info(tickModule, "[Tick#%d] 触发 %s（%s），空闲计数清零", seq, sys.ID(), reason)
		s.run(seq, sys, snap.Now)
		return
	}
	// 规则 2：全部不满足才计入空闲；到阈值后下一次 Tick 由生活体系 Ready 命中
	s.state.IdleTicks++
	s.persistEveryNLocked()
	s.mu.Unlock()
}

func (s *tickScheduler) run(seq int64, sys TickSystem, started time.Time) {
	s.wg.Add(1)
	go func() {
		defer s.wg.Done()
		defer func() {
			if recovered := recover(); recovered != nil {
				logger.Error(tickModule, "[Tick#%d] %s 执行异常: %v", seq, sys.ID(), recovered)
			}
			s.mu.Lock()
			s.busy = false
			s.persistLocked()
			s.mu.Unlock()
			logger.Info(tickModule, "[Tick#%d] 释放 %s，耗时 %v", seq, sys.ID(), time.Since(started))
		}()
		if err := sys.Run(s.ctx); err != nil {
			logger.Warn(tickModule, "[Tick#%d] %s 执行失败: %v", seq, sys.ID(), err)
		}
	}()
}
```

**要点：**

1. `busy` 在锁内、启动 goroutine 之前置 true，保证同一时刻只有一个体系运行。
2. 调度器自身异步执行，`time.Ticker` 不被长模型调用阻塞；后续 Tick 看到 `busy=true` 直接跳过。
3. `IdleTicks` 只在「没有任何体系 Ready」时 +1；任一体系触发立即归零。
4. `Ready` 顺序由 `Priority` 决定；对话 300、观影 200、生活 100。
5. `persistEveryNLocked()` 每 10 个 Tick 落盘一次，状态变化（触发/释放/停止）立即落盘；崩溃最多丢约 9 秒空闲计数。
6. `Stop()` 先 `cancel()`，再 `wg.Wait()`，确保在跑的事件收到取消信号后再退出。

### 3.3 体系适配器（`lunar/tick_systems.go`）

```go
type dialogueSystem struct{}
func (dialogueSystem) ID() string       { return "dialogue" }
func (dialogueSystem) Priority() int    { return 300 }
func (dialogueSystem) Ready(s TickSnapshot) (bool, string) {
	if s.Unread > 0 { return true, fmt.Sprintf("未读消息 %d 条", s.Unread) }
	return false, ""
}
func (dialogueSystem) Run(ctx context.Context) error {
	stateMu.Lock(); reasoningInProgress = true; stateMu.Unlock()
	defer func() { stateMu.Lock(); reasoningInProgress = false; stateMu.Unlock() }()
	incoming := pullContext()
	if len(incoming) == 0 { return nil }
	runDialogueTurn(incoming)
	return nil
}

type viewingSystem struct{}
func (viewingSystem) ID() string    { return "viewing" }
func (viewingSystem) Priority() int { return 200 }
func (viewingSystem) Ready(s TickSnapshot) (bool, string) {
	if s.ViewingPending { return true, "待处理视频切片" }
	return false, ""
}
func (viewingSystem) Run(ctx context.Context) error {
	return BilibiliViewer.RunOneStep(ctx)
}

type lifeSystem struct{}
func (lifeSystem) ID() string    { return "life" }
func (lifeSystem) Priority() int { return 100 }
func (lifeSystem) Ready(s TickSnapshot) (bool, string) {
	if life.HasActiveRun() { return true, "续跑未完成生活事件" }
	if s.IdleTicks >= lifeIdleThreshold { return true, "空闲冷却到期" }
	return false, ""
}
func (lifeSystem) Run(ctx context.Context) error {
	return life.Step(ctx)
}
```

`reasoningInProgress` 保留为兼容量（重载/其他模块读取），但不再作为 Tick 互斥闸门；互斥由调度器 `busy` 承担。

### 3.4 启动与停止

```go
func Start() error {
	...
	tickScheduler = newTickScheduler()
	tickScheduler.Register(dialogueSystem{})
	tickScheduler.Register(viewingSystem{})
	tickScheduler.Register(lifeSystem{})
	mood.Init(context.Background()) // 失败只告警，不阻塞启动
	life.Init()
	go runLoop()
}

func runLoop() {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()
	for {
		select {
		case <-stopCh:
			tickScheduler.Stop()
			return
		case <-ticker.C:
			tickScheduler.Tick()
		}
	}
}
```

## 4. 对话体系接入

### 4.1 从 `dialogueTick` 迁移

删除 `dialogueTick` 中的 `reasoningInProgress` 自旋与 `BilibiliViewer.TickWatch()` 分支；保留其内部逻辑到 `runDialogueTurn`。新的对话适配器负责：

1. `pullContext()` 拉取未读并做资源转换；
2. `runDialogueTurn(incoming)` 跑完整回合；
3. 异常时记录 `lastFailure`，不向调度器抛致命错误（避免 Tick 停摆）。

### 4.2 计划表判定移除

- 删除 `dialogueTick` 里的 `flushDueScheduleItems()` 调用。
- 保留 `checkDueItems()` 与 `flushDueScheduleItems()` 供生活体系调用；函数内部行为不变（到期 ≤ 30 分钟、每日任务按当天时刻、跨日重置）。
- 生活体系在每个事件步骤开始时调用一次 `judgePlans()`，把到期项推入未读队列，并更新未来一小时摘要。

### 4.3 未读消息来源不变

`EnqueueMessage` / `TakeUnreadContext` / `UnreadCount` 保持原样。对话体系只读 `UnreadCount()` 做 Ready 判定，不提前消费；`pullContext()` 仍是唯一消费入口。

## 5. 观影体系接入

### 5.1 现状与目标

现有 `TickWatch()` 是「异步启动一个步骤后立刻返回」，调度器无法用它判断步骤何时结束。需要把它拆成同步语义：

```go
// HasPendingWork 是否还有等待 Tick 的观影步骤。
func HasPendingWork() bool

// RunOneStep 同步执行一个原子步骤；由调度器放在自己的 goroutine 里调用。
func RunOneStep(ctx context.Context) error

// StartLifeRound 生活事件入口：完成启动阶段并留下待处理切片。
func StartLifeRound(moodLabel string) (string, error)
```

`TickWatch()` 可以保留为 `RunOneStep` 的兼容包装，或直接删除（当前只有 `loop.go` 调用，迁移后无调用方）。

### 5.2 `RunOneStep` 的语义

- `manager.mu` 内检查 `job != nil && !manager.running && stepIndex < len(steps)`；
- 置 `manager.running = true`，在锁外执行 `job.runNextStep()`；
- 步骤完成后在 `defer` 里复位 `manager.running`；
- 若 `stepIndex >= len(steps)`，执行 `finishRound()`、清空 `manager.job`；
- 返回错误只记录，不把调度器打挂。

### 5.3 与生活事件「刷视频」的边界

- 生活事件「刷视频」只调用 `StartLifeRound(moodLabel)`，完成打开浏览器、选片、审核、构建 Tick 计划表，返回 `resultText()`（「这次挑了 N 个视频，准备慢慢看…」）。
- 启动产生的待处理切片留在 `manager.job`，下一 Tick 由观影体系以中优先级执行。
- 因此生活事件不会长时间占用 Tick；对话可在切片之间插入，符合高优先级规则。
- 生活体系选中「刷视频」前，调度器已经检查 `ViewingPending=false`，不会在一轮未看完时再开新的一轮。

### 5.4 `StartLifeRound` 的选片输入


这样满足「仅基于配置、记忆、当前心情标签完成选片逻辑」。

## 6. 生活体系

### 6.1 事件定义

```go
// Event 生活事件注册项。
type Event interface {
	ID() string
	Weight() int
	DailyQuota() int
	// Start 创建一次可恢复的事件运行；返回错误表示本次事件无法开始。
	Start(ctx context.Context, env Env) (EventRun, error)
}

// EventRun 一次事件运行。Next 每次只做一个原子步骤。
type EventRun interface {
	Next(ctx context.Context, env Env) (EventStep, error)
	Snapshot() json.RawMessage
	Restore(json.RawMessage) error
}

type EventStep struct {
	Done   bool
	Record string // 完成时要写入的「生活行为记录」
	Detail string // 日志/报告用的细节
}

type Env struct {
	Now       time.Time
	MoodLabel string
	LastRecord string
}
```

### 6.2 内置事件与默认参数

| 事件 | ID | 权重 | 每日额度 | 完成后的生活行为记录 |
|---|---|---|---|---|
| 刷视频 | `watch` | 8 | 6 | `刷了会视频：` + `StartLifeRound` 返回值 |
| 发呆 | `daze` | 100 | 99999 | `发呆中` |
| 逛论坛 | `forum` | 8 | 6 | `逛了论坛：` + `MutualForum.Run` 返回值 |
| 更新心情 | `mood` | 6 | 12 | `出门转了转` |
| 整理记忆 | `memory` | 2 | 2 | `小憩了片刻` |

权重合计 124，发呆占比 80.6% ≥ 75%。当某个事件额度耗尽时，它不再进入候选；发呆始终可用，因此「所有事件额度耗尽」时一定落到发呆。

配置校验：

- 若 `daze.weight / total < 0.75`，启动时告警并回退到默认权重，避免用户配置把发呆比例压到要求以下。
- 额度为 0 的事件视为禁用，不注册。
- 跨自然日按 `Date` 重置所有 `Used`；发呆额度 99999 实际等于无限制。

### 6.3 加权选择

```go
func Pick(st *State) Event {
	avail := make([]Event, 0, len(registry))
	for _, e := range registry {
		if st.Used(e.ID()) < e.DailyQuota() {
			avail = append(avail, e)
		}
	}
	if len(avail) == 0 {
		return dazeEvent // 理论上不会发生：发呆额度视为无限
	}
	total := 0
	for _, e := range avail { total += e.Weight() }
	r := rand.Intn(total)
	for _, e := range avail {
		r -= e.Weight()
		if r < 0 { return e }
	}
	return avail[len(avail)-1]
}
```

选中后**先在锁内** `Used[event]++` 并落盘，再创建运行。额度按「触发」计数，事件失败不退还；日志明确记录 `quota_after`。

### 6.4 一次生活 Tick

```go
func Step(ctx context.Context) error {
	st := loadState()
	judgePlans() // §6.6：到期计划入队 + 未来一小时摘要

	if st.Active == nil {
		event := Pick(st)
		st.Used[event.ID()]++
		run, err := event.Start(ctx, envOf(st))
		if err != nil {
			recordFailure(st, event, err)
			return err
		}
		st.Active = &ActiveRun{Event: event.ID(), Step: 0}
		persist(st)
		logger.Info(lifeModule, "[生活] 开始事件 %s，今日已触发 %d 次", event.ID(), st.Used[event.ID()])
	}

	run := restoreRun(st.Active)
	step, err := run.Next(ctx, envOf(st))
	if err != nil {
		recordFailure(st, activeEvent, err)
		st.Active = nil
		persist(st)
		return err
	}
	if !step.Done {
		st.Active.Step++
		st.Active.Data = run.Snapshot()
		persist(st) // 每步落盘：崩溃后可续跑
		logger.Info(lifeModule, "[生活] 事件 %s 第 %d 步完成：%s", activeEvent.ID(), st.Active.Step, step.Detail)
		return nil
	}
	// 事件完成：写生活记录，释放
	st.LastRecord = step.Record
	st.Active = nil
	persist(st)
	logger.Info(lifeModule, "[生活] 事件 %s 完成，记录=%s", activeEvent.ID(), step.Record)
	return nil
}
```

**释放规则：** `Step` 返回后调度器立即把 `busy=false`，下一个 Tick 重新按优先级判定。未完成事件在下一空闲 Tick 通过 `HasActiveRun()` 续跑，不需要重新等 905 个空闲 Tick。

### 6.5 五个事件的实现

#### 6.5.1 发呆（`event_daze.go`）

- `Start` 返回一个空运行；
- `Next` 直接 `Done=true`，`Record="发呆中"`；
- 不调用模型、不访问网络；可选 `time.Sleep(1-3s)` 让状态机有可观测的耗时，但不阻塞调度器。

#### 6.5.2 更新心情（`event_mood.go`）

- `Start` 记录最新用户发言（`latestUserUtterance()`）；
- `Next` 调用 `mood.UpdateFromText(ctx, text)`；
- 成功：`Done=true`，`Record="出门转了转"`；
- 失败：返回错误，生活体系记 `出门转了转（未完成）`，但保留原心情，不把失败当成功。

`mood` 包只暴露给生活体系调用，对话体系没有更新入口，满足「仅允许生活体系触发」。

#### 6.5.3 逛论坛（`event_forum.go`）

- `Start` 生成内部 instruction：

```
以「{当前心情}」的状态去互助论坛逛一圈：
先看最近的新话题，挑一个感兴趣的读一读；
如果有能接话或能帮上忙的，礼貌回一条；
不要发广告、不要争论、不要暴露自己是程序。
```

- `Next` 调用 `MutualForum.Run(instruction)`；
- 成功：`Done=true`，`Record="逛了论坛：" + truncate(result, 200)`；
- `MutualForum.Ready()` 为 false 时直接失败，日志说明论坛不可用；额度仍消耗（按触发计）。

#### 6.5.4 刷视频（`event_watch.go`）

- `Start` 记录 `moodLabel`；
- `Next` 调用 `BilibiliViewer.StartLifeRound(moodLabel)`；
- 成功：`Done=true`，`Record="刷了会视频：" + result`；
- 返回的 `result` 是启动阶段文本，待处理切片由观影体系接管（§5.3）；
- 失败：记录 `刷了会视频（未完成）：<原因>`，日志写清浏览器/选片/审核哪一步失败。

#### 6.5.5 整理记忆（`event_memory.go`）

- `Start` 枚举全部文本记忆，排除哔哩观影记忆，构建批次，保存初始快照；
- `Next` 每次处理一个批次（§8）；全部批次完成时 `Done=true`，`Record="小憩了片刻"`；
- 无符合条件的记忆：直接 `Done=true`，记录仍为 `小憩了片刻`。

### 6.6 计划表逻辑迁移

`engine/life/plan.go` 提供两个函数，只在 `life.Step` 开头调用：

```go
// JudgePlans 到期项入未读队列；同时刷新未来一小时摘要。
func JudgePlans(now time.Time) (summary string)

// UpcomingSummary 未来 window 内即将触发的计划摘要；没有则返回 ""。
func UpcomingSummary(now time.Time, window time.Duration) string
```

规则：

1. 沿用 `checkDueItems()`：`now >= due` 且 `now-due <= 30 分钟` 才触发；超过 30 分钟视为错过；
2. 到期项以 `scheduleTriggerPrefix` 推入 `unreadContext`，`source=schedule`，不写前端对话缓存；
3. 未来一小时内（`due > now && due <= now+1h`）的计划按时间排序，拼成 `"HH:MM 内容；HH:MM 内容"`；
4. 没有未来计划时，全局消息的 `PlanSummary` 字段置为 `""`，渲染时显示「无」；
5. 摘要写入生活状态，对话运行时消息读取它；不每次对话实时重算，保证「仅在生活体系运行时判定」。

**风险与兜底：** 905 秒冷却约 15 分钟，小于 30 分钟宽限，正常不会丢计划；若生活体系被禁用或长时间被高优先级体系占用，计划可能超过 30 分钟。此时：

- 日志告警 `[计划表] 到期项错过宽限`；
- 当前没有 `life.enabled` 开关，因此不注册 `planOnlySystem`；将来若增加禁用开关，再补一个只做 `JudgePlans` 的低优先级体系即可。

### 7.3 更新规则

只由生活事件「更新心情」调用：

```go
func UpdateFromText(ctx context.Context, text string) error {
	text = strings.TrimSpace(text)
	if text == "" { return nil } // 没有最新发言，不更新
	uVec, err := memory.EmbedDocuments(ctx, []string{text})
	if err != nil { return err }

	sims := make([]float64, len(labels))
	for i, label := range labels {
		sims[i] = cosine(uVec[0], state.Base[label])
	}
	probs := softmax(sims, temperature) // temperature 默认 0.15
	target := make([]float32, dim)
	for i, label := range labels {
		for d := range target {
			target[d] += float32(probs[i]) * state.Base[label][d]
		}
	}
	next := normalize(lerp(state.Vector, target, 1-alpha)) // alpha 默认 0.7，保持心情惯性
	label := argmaxCosine(next, state.Base)
	// 先写内存 + 落盘，再返回；失败保留旧值
}
```

参数默认值：

| 参数 | 默认 | 说明 |
|---|---|---|
| `alpha` | 0.7 | 当前心情权重；越大越稳定 |
| `temperature` | 0.15 | 情绪分布锐度；越小越接近最强情绪 |
| `labels` | 开心/愤怒/伤心/好奇/无聊 | 固定 5 类，不开放任意标签 |

**标签匹配：** `argmax cosine(next, base[label])`；余弦相同按 `probs` 高者优先，再按固定顺序兜底。标签只用于全局消息与选片，不参与记忆写入。

**「对应情绪嵌入向量」的解释：** 先用最新发言的嵌入得到 5 类情绪分布，再以分布加权合成 `target` 向量，最后与当前心情做加权平均。这样既利用了发言语义，也保持了心情的连续性。

### 7.4 最新发言来源

- `latestUserUtterance()` 优先返回内存值；为空时从 `cachedMessages` 倒序找最近一条用户文本；
- 不持久化原始发言，避免重复存储；重启后从对话缓存恢复。

## 8. 记忆整理事件

### 8.1 数据范围

1. 分页枚举 `memory.List("text", offset, 200)` 直到取完；
2. 排除：
   - `entry.Source == "bilibili_viewer"`；
   - 正文以 `[B站视频]` 开头的条目（双保险，防止历史数据缺 source）；
3. 其余全部文本记忆按 `Timestamp` 升序进入批次，保留 ID 与正文快照。

### 8.2 分批算法（`memory_batch.go`）

```go
const batchMaxRunes = 10000

func BuildBatches(entries []memory.Entry) []Batch {
	var out []Batch
	var cur Batch
	curRunes := 0
	for _, e := range entries {
		n := utf8.RuneCountInString(e.Content)
		if curRunes > 0 && curRunes+n > batchMaxRunes {
			out = append(out, cur); cur = Batch{}; curRunes = 0
		}
		cur.Entries = append(cur.Entries, e); curRunes += n
		if n > batchMaxRunes {
			// 单条超限：独占一批，保证条目不截断
			out = append(out, cur); cur = Batch{}; curRunes = 0
			logger.Warn(lifeModule, "[记忆整理] 单条记忆 %s 超过 %d 字符，独占一批", e.ID, n)
		}
	}
	if len(cur.Entries) > 0 { out = append(out, cur) }
	return out
}
```

硬约束：**批次按字符数（rune count）计算；任何单条记忆不跨批、不截断。**

### 8.3 模型调用

每个批次一次 `primary_reasoning` 调用，使用生活人设 + 整理任务：

```
你是月华的记忆整理助手。下面是一批旧记忆，请完成：
1. 去重与相似合并；
2. 只保留值得长期记住的内容（人物、关系、事件、偏好、承诺、明确观点）；
3. 丢弃寒暄、重复、临时过程、机械统计、无信息量内容；
4. 用月华第一人称、口语化、自然中文复述；
5. 每条 20-160 字，不编号、不加标签、不解释；
6. 只输出 JSON 字符串数组；没有值得保留的内容输出 []。
```

用户消息按 `- 正文` 逐条列出；不把 ID 交给模型，避免模型复述 ID。

解析与校验：

- 去掉 ```json 围栏；
- 取第一个 `[` 到最后一个 `]`；
- `json.Unmarshal` 为 `[]string`；
- 去空白、去重、过滤超长（>500 字符截断到句末或丢弃）；
- 解析失败重试 1 次；仍失败则本批不删除、不写入，事件失败并保留旧记忆。

### 8.4 事务与恢复（`memory_journal.go`）

因为 `AddText` 会对已有内容做 0.98 相似去重，**必须先删除旧条目再写新条目**，否则新内容会被判定为旧内容的重复而不写入，随后旧条目被删，数据丢失。为保证崩溃安全，使用批次意图日志：

```go
type Journal struct {
	BatchID    string        `json:"batch_id"`
	Status     string        `json:"status"` // prepared | deleted | written | done
	OldEntries []JournalItem `json:"old_entries"` // id/content/role/timestamp 全量快照
	NewTexts   []string      `json:"new_texts"`
	WrittenIDs []string      `json:"written_ids"`
	DeletedIDs []string      `json:"deleted_ids"`
	UpdatedAt  int64         `json:"updated_at"`
}
```

单批流程：

1. **prepared**：把旧条目完整快照写入 `database/life_chain/memory_journal/<batch>.json`；
2. **删除**：逐条 `memory.Delete(ctx, id)`；任一失败则保持 `prepared`，中止本批，下次重试；全部成功则 `deleted`；
3. **写入**：逐条 `memory.AddText(ctx, "assistant", text)`（不传 tags、不传 source）；记录 `WrittenIDs`；全部成功则 `written`；
4. **完成**：状态 `done`，删除日志文件（或保留最近 3 天供审计）。

启动恢复（实现按「继续完成」处理，避免已删除的旧条目丢失）：

- `prepared` / `deleted` / `write_failed`：继续删除剩余旧 ID → 写 `NewTexts` → 删除日志；
- `done`：直接删除日志；
- 每个删除完成后都会更新日志里的 `DeletedIDs`，所以崩溃在删除中途也能继续；
- 写入持续失败时保留日志，下一次生活事件或启动时继续重试；`AddText` 的 0.98 去重保证重复写入不会产生重复条目。

这样满足：

- 全部旧条目删除后写新条目；
- 崩溃后可恢复；
- 写入不附加任何标签/来源；
- 新记忆仍会被下一次整理再次纳入。

### 8.5 完成回调

所有批次 `done` 后，`EventStep{Done:true, Record:"小憩了片刻"}`。中途失败则 `Record="小憩了片刻（未完成）"`，并把失败批次号写日志；已完成的批次不回滚。

## 9. 状态、持久化与原子性

### 9.1 文件布局

```
local_data/database/
├── tick_state.json                    调度器空闲计数/上次触发
└── life_chain/
    ├── life_state.json                日期、额度、未完成事件、生活记录、计划摘要
    ├── mood_state.json                基础情绪向量、当前心情、标签
    └── memory_journal/
        └── <batch-id>.json            记忆整理批次意图日志
```

全部位于已 gitignore 的 `local_data/database/` 下，不需要新增忽略规则。

### 9.2 原子写

新增 `engine/persistence/atomic.go`：

```go
func WriteFileAtomic(relPath string, data []byte) error {
	full := filepath.Join(config.LocalDir, filepath.FromSlash(relPath))
	if err := os.MkdirAll(filepath.Dir(full), 0o755); err != nil { return err }
	tmp := full + ".tmp"
	if err := os.WriteFile(tmp, data, 0o644); err != nil { return err }
	if err := os.Rename(tmp, full); err != nil { // Windows 下 rename 覆盖已有文件
		_ = os.Remove(full)
		if err2 := os.Rename(tmp, full); err2 != nil { return err2 }
	}
	return nil
}
```

- 所有状态文件先写临时文件再 rename；
- 调度器、生活、心情各自持有自己的 `sync.Mutex`，不跨包持锁；
- 记忆库自身已有集合级锁，整理事件不额外加全局锁，避免与普通写入互锁。

### 9.3 重启恢复

| 状态 | 恢复行为 |
|---|---|
| `tick_state.json` 损坏 | 重置 `IdleTicks=0`，告警 |
| `life_state.json` 日期不是今天 | 重置 `Used`，保留 `LastRecord` / `PlanSummary` |
| `life_state.json` 有 `Active` | 按事件 ID 重建 `EventRun` 并 `Restore`；失败则清空并记录 `interrupted` |
| `mood_state.json` 模型名/维度不一致 | 重新计算基础向量，按开心偏向初始化 |
| 记忆整理日志残留 | 按 §8.4 恢复；无法恢复则回滚旧条目 |

### 9.4 并发边界

- Tick 调度：单 goroutine `Tick()` + `busy` 闸门；
- 生活事件：调度器 goroutine 内串行执行，事件内部不再起并发；
- 心情：`mood.mu` 保护 State；
- 记忆整理：只由生活事件串行调用；普通记忆写入由对话/记忆流程并发，依赖记忆库集合锁；
- 重载：`reload.go` 停止旧调度器 → `cancel` + `wg.Wait()` → 新调度器从持久化状态恢复；`reasoningInProgress` 复位。

## 15. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 长模型调用占用 Tick | 对话延迟 | 事件拆原子步骤；每步返回即释放；对话在步骤边界抢占 |
| 905 秒冷却导致计划晚到 | 计划提醒延迟 ≤ 15 分钟 | 沿用 30 分钟宽限；超宽限告警；当前无禁用开关，后续加开关时再补 `planOnlySystem` |
| 记忆整理先删后写崩溃 | 记忆丢失 | 批次意图日志 + 旧条目快照 + 启动恢复/回滚 |
| 0.98 去重误判 | 新记忆写不进 | 必须先删旧再写；日志记录 `AddText` 返回的既有 ID |
| 嵌入服务不可用 | 心情无法初始化/更新 | 启动降级为「开心」；下次生活事件重试；更新失败保留旧心情并记录 |
| 模型输出不是合法 JSON | 整理批次失败 | 重试 1 次；仍失败保留旧批次，不写不删 |
| 多体系注册冲突 | 重复触发 | `Register` 按 ID 去重；优先级稳定排序 |
| 状态文件损坏 | 重启行为异常 | 原子写 + 损坏降级默认值 + 告警 |
| 生活事件内部再起并发 | 破坏单占用 | 事件实现禁止 goroutine；调度器串行调用 |
| 计划表迁移后对话不再 flush | 旧行为变化 | 只在生活体系判定；905 秒冷却小于 30 分钟宽限 |
| 观影启动失败 | 生活事件失败 | 记录失败原因；额度按触发计；下次重新选择 |
| 论坛不可用 | 生活事件失败 | `MutualForum.Ready()` 预检；失败记录，不阻塞后续事件 |
