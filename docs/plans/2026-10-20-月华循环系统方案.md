## 0. 结论摘要

本次做两件事：

1. **生活链骨架**：与思维链并列的第二个循环体系；同一时刻只能有一个循环在跑；生活链内部顺序执行，不引入新运行时/并发模型。
2. **生活链第一条场景：B 站刷视频**：多时间段触发、每段独立额度、选片 → 观看 → 读热评 → 评论判断 → 间隔 → 下一个 → 动态 @ 分享 → 看动态回复并社交 → 写 200 字日记。

**不做**：记忆蒸馏（记忆库整理）仍暂缓；本次只写“生活链日记”这一条普通记忆，不改记忆库结构、不做全库整理。

**本次已拍板（v6）：**

| 议题 | 结论 | 落点 |
|---|---|---|
| 失联策略 | 硬上限 **45 分钟**；每个视频之间检查未读，有人在等就提前收摊 | §5.2 / §6.5 / §10 |
| 聊天里的 B 站链接 | ≤600 秒现场看；更长只回“还没看过”并记 `watchLater` | §7.4 |
| 写操作首批 | 评论与动态**都先 `dry_run`** 观察 2–3 天，之后再逐个开真发 | §6.4 / §6.6 / §10 |

可行性判断：

| 能力 | 结论 | 依据 |
|---|---|---|
| 账号登录 | **可行** | 浏览器登录后取 cookie（SESSDATA + bili_jct + buvid3），独立文件保存；`nav` 校验 |
| 看视频 | **高可行** | `view`/`related`/`playurl` 可用；CDN 必须带 Referer；`ffmpeg -t 600` 只拉前 10 分钟已实测 |
| 选视频 | **可行** | 种子 + related；登录后可加 WBI 搜索/热门/排行 |
| 写评论 | **可行但有风险** | cookie + CSRF（**不需要 WBI**）；验证码/限流；默认 dry-run、小号、失败即停 |
| 发动态 + @ | **可行但公开可见** | `dynamic_svr/create` 的 `content/at_uids/ctrl` 有文档示例；`type=1 + rid=aid` 视频卡需真实账号验证 |
| 动态回复 + 社交 | **可行，需验证评论类型** | 动态评论 `type=17`、`oid=dyn_id`；回复用 `x/v2/reply/add` |
| 视频理解 SQL 缓存 | **可行，复用现有 media.db** | `video_summary` 已迁入 `media.db`，仍由 `knowledgeLoad('video_summary')` 路由；加 URL 归一化即可复用 |
| 循环互斥/消息暂存 | **可行** | 现有 Go 未读队列已满足“不消费” |

**工期**：MVP（生活链骨架 + 看视频 + 动态 @，先单窗口跑通）约 **2 周**；多窗口/评论/社交/缓存完善约 **3–3.5 周**（单人）。

三个主要风险：

1. **动态是公开的**：@ 所有人可见，比私信更容易被判营销/骚扰；必须低频、固定目标、内容克制。
2. **写接口风控**：动态/评论/回复都是高风险；未绑定手机 `4126021`、CSRF `-111`、限流等要按错误码停手。
3. **本机观看成本**：10 分钟视频 = 8 段 × 80 秒多模态推理，墙钟可能 5–15 分钟；内容时长与分段数是**唯二能硬控**的预算（视频内无法中断，见 §6.3），另设 45 分钟总墙钟与未读退出兜底。

## 1. 命名与定位

### 1.1 两套循环体系

| 体系 | 职责 | 现有实现 |
|---|---|---|
| **思维链** | 对话、思考、工具调用、回应消息 | 现有 `thoughtLoopTickEvent`，1 秒 tick，消费 `UnreadContext` |
| **生活链** | 月华“自己过日子”：刷视频、看评论、发动态、社交、写日记 | 本次新增，与思维链并列；第一条场景是 B 站 |

- 代码命名：`LoopMode = 'thinking' | 'lifechain'`；`lifechain.scenario = 'bilibili'`。
- 用户可见文案仍可用“逛 B 站”；体系名叫“生活链”。
- 生活链以后可以扩展第二条场景（看番、听歌、逛论坛），但本次只做 B 站，**不预造用不上的抽象**。
- 两者**不能同时运行**：思维链空闲时生活链才能进入；生活链运行中思维链 tick 直接 return。
- 生活链不是“思维链的一个角色”，而是并列循环；不改造思维链的对话/工具逻辑，只加一个模式闸门。

### 1.2 为什么叫“生活链”

- 思维链是“被消息驱动的思考”；
- 生活链是“到点自己决定去做点什么”的主动生活；
- B 站刷视频只是第一条生活链，后续可以并行扩展，但调度/额度/报告/日记的骨架共用。

### 2.3 A2A 的边界

- 生活链四个角色**不互相直接调用**：只通过 `LifeChainBus.send()` / `request()` 收发消息。
- Bus 是**生活链内部**的顺序消息队列：`send` 入队，director 逐条 `await`，没有并行、没有后台线程。
- 模型调用仍是 `ModelBuilder.run`（同步 `syncFetch`），与现有子智能体一致；Bus 不包一层新的模型协议。
- 思维链仍用现有 `dispatch_*` 直接调用；**不把思维链改成消息总线**。
- 如果实现时发现 Bus 与现有单线程节奏冲突，以现有实现为准：退化为 director 直接调用四个角色的 `handle()`，消息仍作为参数传递。

> **v6 结论：不建 `lifechain/bus.ts`。** 现有子智能体就是 `await role.createCreativeWork(...)` 式直接调用（[agent-control.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/tools/agent-control.ts#L97-L100)），生活链照抄这个形状即可：director 顺序 `await` 四个角色，消息作为参数传。本节其余内容是"如果以后真需要并发"时的边界说明，本次不实现。

### 2.4 入口与退出

- 思维链 `thoughtLoopTickEvent` 顶部只加一行：`if (GlobalConfig.loopMode !== 'thinking') return;`
- 生活链运行中不调用 `pullContext`；退出后把 `loopMode` 复位，下一次 tick 自然拉消息。
- 不改 `reasoningInProgress` 语义；生活链进入条件包含 `!reasoningInProgress`。
- 引擎重载时 `ResetLifeChainState()`；新运行时读 `state.json`，把 `running` 改 `interrupted`，不自动续跑。

### 2.5 数据库与记忆库最新架构（本次核对）

这次代码变更（`1600abc9`）把数据库和记忆库都改了；生活链必须按新架构落：

#### 2.5.1 数据库按领域分文件（ADR 0009）

| 库文件 | 领域 | 表 |
|---|---|---|
| `media.db` | 媒体派生数据 | `video_summary`、`vision_cache` |
| `knowledge.db` | 用户/插件自建表 | 无内建表 |
| `archive.db` | 统一资源名录 | `resources`、`resource_sections` |
| `web.db` | 网络检索缓存 | `web_ltp_page_cache` |
| `text.db` | 文本索引 | `file_mapping` |
| `character.db` | 自定义角色 | `painter_characters` |

- `knowledgeLoad('video_summary')` 仍可用，但实际落 `media.db`（`knowledgeBuiltinTables` 路由）。
- **新增表必须先登记到 `domain_db.go` 的领域 schema**，不能塞 `knowledge.db`。
- 本次**不新增表**：B 站视频理解直接复用 `video_summary`；标题/热评/动态 id 放 `seen.json` 与报告，不进 SQL。这样不重复存摘要，也不触发建表/迁移。

#### 2.5.2 记忆库改为“自动分组 + 全局类型化检索”

| 变更 | 影响 |
|---|---|
| 不再有 `lunar_messages` 这类固定集合 | 写入时按内容向量与集合名向量自动归组 |
| 默认分组是中文语义组：日常闲聊/人物信息/关系互动/情感心情/兴趣爱好/偏好习惯/观点态度/动作行为/事件经历/计划日程/工作学习/知识见闻/地点场景/表情包/图片素材/截图/绘画作品/语音消息/音乐音频/环境声音 | 日记会自动落到“事件经历/日常闲聊”等最相关组 |
| `memoryAdd(role, content)` 2 参数 | **不能再传集合名** |
| `memoryAddWithTags(role, content, tags, source)` | tags 会参与嵌入与 0.98 去重；**日记不要用固定 tags**（否则第二篇会被判重复） |
| `memoryQuery(queryText, mediaType, topK)` | 查询不再传集合名，只传类型 `text/image/audio` |
| `memoryKeywordSearch(mediaType, terms, useRegex, limit)` | 同上 |
| 新增 `memoryGet(id)` / `memoryList(mediaType, limit, offset)` | 可按 ID 取、逐条列举 |
| `search_memory` 只检索文本类型、跨全部组 | 日记写文本类型即可被 `search_memory` 找到 |

**对生活链的影响：**

1. 日记写 `memoryAdd('assistant', diary)`：正文参与嵌入与自动归组，每篇日记内容不同，不会被 0.98 去重误判；
2. 不要用固定 tags 写日记（`memoryAddWithTags` 会用 tags 做嵌入，固定 tags 会让第二篇日记被当成重复）；不再出现 `lunar_messages`；不要给 `memoryAdd` 传集合；
3. 视频摘要仍写 `video_summary`（media.db），`getPromptFromKnowledge` / `getPromptFromKnowledgeAny` 继续可用；
4. 以后恢复记忆蒸馏时，用 `memoryList('text', ...)` + `memoryGet` + `memoryDelete` + `memoryAdd`，不按集合名操作；不要用固定 tags 批量写（同样会被 0.98 去重误判）。

```json
  "ac_time_value": "",
  "updated_at": "2026-10-20T13:00:00+08:00"
}
```

- `.gitignore` 增加 `local_data/bilibili_account.json`。
- `lunar_config.json` 只放 `life_chain.bilibili.account.credentials_file` 指针和 `uid/uname` 非敏感信息。
- 日志/报告只显示 `uid`/`uname`；异常信息对 `SESSDATA`/`bili_jct` 脱敏。
- 可选：`icacls` 限制文件为当前用户。

### 4.2 登录预检

```
GET https://api.bilibili.com/x/web-interface/nav
Cookie: SESSDATA=...; bili_jct=...; buvid3=...; dedeuserid=...
```

| 结果 | 处理 |
|---|---|
| `isLogin=true` | 记录 `mid`/`uname`/`mobile_verified`；`uid` 不一致以 `nav.mid` 为准 |
| `isLogin=false` / `-101` | 停评论/动态/回复；`require_login=true` 时当天窗口跳过 |
| `mobile_verified=false` | 动态/评论会失败（`4126021`）；停写操作 |
| 网络失败 | 重试 1 次；仍失败则本窗口跳过写操作 |

### 4.3 目标账号

`targets` 是数组，允许配置多个：

```json
"targets": [
  { "uid": 987654321, "name": "目标A" },
  { "uid": 123123123, "name": "目标B" }
]
```

- 每条动态只 @ **一个**目标（默认随机；可配 `target_pick: "first"`）。
- `name` 可手填；为空时用 `web-interface/card?mid=<uid>` 或 WBI `space/wbi/acc/info` 取。
- 目标 = 自己 → 跳过；昵称取不到 → 跳过动态（不裸发 `@uid`）。
- 动态 @ 不要求互关（与私信不同）；但公开 @ 仍需低频、固定对象。

## 5. 生活链调度：多时间段 + 独立额度

### 5.1 时间段配置

一天可以配置多个时间段；每个时间段**只触发一次**；每个时间段**额度独立**。

```json
"windows": [
  {
    "id": "morning",
    "start": "10:40",
    "end": "11:10",
    "skip_probability": 0.25,
    "watch_min": 1,
    "watch_max": 3,
    "comment_max": 1,
    "dynamic_max": 1,
    "social_max": 2
  },
  {
    "id": "afternoon",
    "start": "15:30",
    "end": "16:00",
    "skip_probability": 0.25,
    "watch_min": 1,
    "watch_max": 2,
    "comment_max": 1,
    "dynamic_max": 1,
    "social_max": 1
  }
]
```

| 字段 | 说明 |
|---|---|
| `start`/`end` | 时间段；到点后在区间内随机取一分钟作为本窗口触发点 |
| `skip_probability` | 本窗口“今天不刷”的概率；每个窗口独立 |
| `watch_min`/`watch_max` | 本窗口观看目标/上限；`watch_max` 是硬上限，`watch_min` 是期望值（可提前停） |
| `comment_max` | 本窗口评论上限 |
| `dynamic_max` | 本窗口动态上限（0 或 1；一条动态只 @ 一个目标） |
| `social_max` | 本窗口对动态回复的社交上限（1–2 条） |

- 时间段建议**不重叠**；重叠时先进入的窗口占用生活链，后一个窗口到点若仍忙则记 `busy`，不排队。
- **必须避开每日计划**：`PRESET_DAILY_TASKS` 在 06:30 / 08:00 / 10:00 / 12:00 / 15:00 / 17:30 / 22:30 有固定问候（[defs.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/tools/schedule/defs.ts#L27-L35)）。窗口起始若贴着这些时刻，问候会被压到生活链结束后才发出（最多晚 45 分钟）。因此默认窗口取 **10:40–11:10 / 15:30–16:00**，与 10:00、15:00 各留 30 分钟间隔。
- 每个窗口的额度独立；日报里按窗口汇总。
- 每天总观看量 = 各窗口 `watch_max` 之和；不再设全局 `min_videos/max_videos`。

### 5.2 计划文件

`local_data/database/life_chain/plan.json`：

```json
{
  "date": "2026-10-20",
  "windows": [
    {
      "id": "morning",
      "at": "10:47",
      "decided": true,
      "go": true,
      "entered": true,
      "status": "done",
      "used": { "watch": 2, "comment": 1, "dynamic": 1, "social": 1 },
      "endReason": "quota"
    },
    {
      "id": "afternoon",
      "at": "15:12",
      "decided": false,
      "go": null,
      "entered": false,
      "status": "pending",
      "used": { "watch": 0, "comment": 0, "dynamic": 0, "social": 0 },
      "endReason": null
    }
  ]
}
```

- 启动时若日期不是今天 → 重新生成本日全部窗口的 `at`；同一天重启复用，不重新随机。
- 每个窗口 `at` 到点：
  1. 先检查 `loopMode==='thinking'`、`!reasoningInProgress`、`unreadCount()===0`；不满足则每 30 秒重试，最多 `entry_wait_minutes`；超时 → `status="busy"`，窗口结束（不消耗随机机会）。
  2. 思维链空闲后，若 `decided=false`：按 `skip_probability` 决定去不去；不去 → `status="skip"`，窗口结束。
  3. 去 → `loopMode='lifechain'`，进入刷视频流程。
- 错过窗口：`grace_minutes`（默认 120）内启动可补跑；超过 → `status="missed"`。
- **运行期退出口（v6）**：进入生活链后，每看完一个视频就在间隔前检查 `unreadCount()`：
  - `>0` → 结束观看循环，`endReason="message_waiting"`，把动态/社交/日记跑完立刻退出，回到思维链应答；
  - 同时检查墙钟 `max_run_minutes`（默认 45）→ 超时 `endReason="timeout"`，同样走收尾流程。
  - 这段"收尾"必须**不可省略**：动态/社交/日记照跑，只是不再开新视频，否则窗口常常只剩一份空报告。
- 一个窗口结束后，其他窗口仍按各自时间触发；若后一个窗口到点时前一个还在跑，记 `busy`。

### 5.3 额度账本

`local_data/database/life_chain/quota.json`：

- 每个窗口独立账本；窗口结束写 `plan.json` 的 `used`。

- 同一 BV 7 天内不重复评论/动态。

## 6. B 站刷视频流程

### 6.1 总流程

```
窗口到点 → 等思维链空闲 → 决定去不去 → 进入生活链
  → 选片者选一个视频
  → 观看者看（≤10 分钟内容）+ 读热评 + 写 SQL 缓存
  → 评论者判断是否评论（额度内）
  → 等待 90–300 秒
  → 还有观看额度且未决定提前停 → 回到“选片者”
  → 观看结束 → 分享者从看过的视频里挑一个，决定是否发动态 @ 目标
  → 若发了动态 → 查看动态回复 → 有回复就社交（额度内）
  → 写 200 字日记到记忆库
  → 写报告 → 退出，回到思维链
```

### 6.2 选片者（Curator）

输入：本窗口已看 BV、`seen.json`、种子、偏好关键词、候选池。

候选来源：

1. 配置种子 `seeds`（5–20 个，覆盖游戏/音乐/科技/生活）；
2. 已看视频的 `related` 图（每次约 30 条，自增长）；
3. 登录后可选 WBI 搜索/热门/排行（Phase 2）。

过滤（不调模型）：

| 规则 | 说明 |
|---|---|
| 已看 | `seen.json` TTL 内（默认 30 天） |
| 时长 | `duration > 4h` 或 `videos > 20`（明显直播回放/合集） |
| 付费/充电 | `rights.pay` / `is_upower_exclusive` / `is_upower_play` / `is_chargeable_season` |
| 状态 | `state != 0`、`duration <= 0` |
| 关键词 | `blocked_keywords`（直播回放/录播/付费/充电专属等） |
| 同一 UP | 同一天最多 1–2 条 |
| 候选耗尽 | 刷新 related；仍不足则本窗口 `endReason="no_candidates"` |

选片：过滤后**均匀随机**抽一个；不按固定顺序、不按播放量排序。

### 6.3 观看者（Viewer）

1. 解析 URL：`BV` / `av` / `b23.tv` 短链；统一为 `https://www.bilibili.com/video/<BV>`。
2. `view` 取 `aid/cid/duration/pages/rights/owner/desc`；多 P 默认第 1 P。
3. `playurl` `qn=32`（360P）、`fnval=1`、`platform=html5`；实测 890 秒约 14MB，600 秒约 9–10MB。
4. Go `ffmpeg -headers "Referer: https://www.bilibili.com" -i <durl> -t min(duration,600) -c copy <out.mp4>`；**只拉前 600 秒**。
5. `videoMedia(out.mp4)` → 80 秒/段；按 `watch_segments`（默认 8，可 6）取子集，传给现有 `perceiverRole.watchVideo(mediaUrls)`；**不改 `watchVideo` 签名**。
6. 读热评：`reply?type=1&oid=<aid>&sort=2&ps=20`，取前 8 条（作者/正文/点赞）。
7. 写入 SQL 缓存（见第 7 节）。
8. 产出 `watch_result`：标题/UP/时长/实际观看/是否截断/分段/墙钟/摘要/热评/错误。

**三层预算：**

| 维度 | 默认 | 说明 |
|---|---|---|
| 内容时长 | 600 秒 | 只理解前 10 分钟；短视频看完即止 |
| 分段数 | 8（可配 6） | 只把子集传给感知者，控制模型调用次数 |
| 墙钟预算 | 每视频 15 分钟 | director 在视频之间检查；视频内靠分段数兜底 |

> **v6 更正：三层里只有前两层是硬控。** `perceiverRole.watchVideo` 在内部逐段同步调用模型（[perceiver.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/roles/perceiver.ts#L38-L64) → `run()` → `syncFetch`，单次超时 300 秒），JS 侧**无法在段与段之间打断**。所以"单视频 15 分钟"只能在视频之间检查，真正的护栏是内容时长（600 秒）与分段数（≤8）。实现时不要假装能掐断视频内的推理。

- 短视频（<600 秒）：全部分段；`truncated=false`。
- 长视频：只看前 600 秒；`truncated=true`。
- 观看失败（下载/解析/理解为空）：跳过，记 `error`；**连续两次失败 → 本窗口提前收摊**。
- 观看成功计入 `watch_used`；失败不计额度。

### 6.4 评论者（Commenter）

输入：`watch_result` + 人设片段 + 本窗口 `comment_used/comment_max` + 已评记录。

判断：

- 值得评：有具体观点/情绪/信息增量；能接住视频内容或热评；不是“好看/支持”空话。
- 不值得评：内容太浅、看不懂、争议大、需要专业知识、只是音乐/画面无话可说、评论区已一边倒。
- 输出 JSON：`{"decision":"post|skip","reason":"...","text":"..."}`；解析失败重试一次，仍失败则 skip。

发布前校验：

| 检查 | 处理 |
|---|---|
| 长度 | 1–120 字（按 code point） |
| 禁用词 | AI/模型/程序/系统/工具/提示词；政治/医疗/金融建议；引战/人身攻击 |
| 链接/@ | 不允许 |
| 重复 | 与最近 30 天已发评论相似度 ≥0.90 拒发 |
| 额度 | 本窗口 `comment_used < comment_max`；同一 BV 7 天一次 |
| 账号 | 登录有效；否则 skip（reason=`no_login`） |
| dry-run | `comment.dry_run=true` 只记录不发送 |

发布：Go `biliPostComment(aid, message)`（cookie + CSRF + WBI + 限频 + 错误映射）。成功返回 `rpid`；失败按错误码停发本窗口评论。

### 6.5 循环、间隔、收摊

- 每看完一个视频：
  - `watch_used++`；
  - 若 `watch_used >= watch_max` → 退出观看循环；
  - 若 `watch_used >= 1` 且 `Math.random() < stop_probability`（默认 0.08）→ `endReason="mood"`，提前结束观看；
  - 否则 `await sleep(random(gap_seconds))`（90–300 秒），继续下一个。
- 硬收摊：`max_run_minutes`（默认 **45**）、连续两次观看失败、候选耗尽、观看额度用完、**有未读消息**（`endReason="message_waiting"`，见 §5.2）。
- 评论/动态/社交额度不影响观看循环；评论用完仍可继续看，只是不再评。

### 6.6 动态 + @（分享者 Sharer）

观看循环结束后：

1. 若 `dynamic_max=0` 或本窗口没有成功观看的视频 → 跳过动态，记原因。
2. Sharer 从本窗口看过的视频里挑 **一个**（可综合考虑摘要质量/热评/新鲜度；默认随机或最近一个），判断值不值得发动态。
3. 输出 JSON：`{"decision":"share|skip","reason":"...","text":"..."}`；`text` 不含 @ 和链接，由程序拼接。
4. 从 `targets` 里选一个目标（`target_pick: "random" | "first"`）。
5. Go `biliPublishDynamic(targetUid, targetName, aid, bvid, text, mode)`：
   - `mode="video"`：`type=1`、`rid=<aid>`、`content=text + " @" + targetName`；
   - 失败退回 `mode="text"`：`type=4`、`rid=0`、`content=text + " @" + targetName + " " + url`；
   - `at_uids=<targetUid>`；`ctrl=[{location,length,type:1,data:<targetUid>}]`；
   - 成功记 `dynamic_id_str`/`dynType`；失败按错误码停发本窗口动态。
6. `dynamic_used++`；同一条动态只 @ 一个目标。
7. **首批 `share.dry_run=true`（v6）**：只生成文案、做 `ctrl`/长度/`@` 校验、写进报告，**不调** `biliPublishDynamic`；`dynamic_used++` 照记，用来观察额度节奏与文案质量。观察 2–3 天确认措辞对味后再开真发，且先只开动态、最后再开评论。

**一个还是多个**：默认 `target_mode: "one"`，一条动态只 @ 一个目标；`targets` 允许多个，是给不同窗口轮换用。若你确实要同条 @ 多人，改 `target_mode: "all"`，`at_uids` 用逗号拼接、`ctrl` 里放多条 `@` 记录（每条动态仍受 300 字和 1–2 条/窗口限制）。多目标 @ 更容易被视为刷屏/骚扰，默认不推荐。

### 6.7 查看动态回复 + 社交（Sharer 的第二段）

1. 若本窗口发了动态：
   - 等待 30–90 秒，让评论有机会出现；
   - `GET https://api.bilibili.com/x/v2/reply?type=17&oid=<dyn_id>&sort=2&ps=20` 取回复（动态评论类型 `17`，需真实账号验证）；
   - 过滤：不是自己、不是纯表情/广告/引战；优先回复“问问题/提到月华/友好互动”的。
2. 若有可回复的：
   - 生成 1 句回复（≤80 字，人设，不引战、不暴露 AI）；
   - `POST https://api.bilibili.com/x/v2/reply/add`，`type=17`、`oid=<dyn_id>`、`message`、`root=<rpid>`、`parent=<rpid>`、`csrf`；
   - `social_used++`，直到 `social_max`。
3. 若没有回复：记 `no_replies`，结束社交阶段。
4. 可选：如果本窗口没发动态，检查最近 `social.lookback_hours` 内自己发的动态，有回复也社交（默认关闭，避免每窗口重复打扰）。

**社交原则**：只回友好/提问；不争论、不删评、不 @ 无关人；一条动态最多回 `social_max` 条；失败即停，不刷屏。

### 6.8 日记（写记忆库）

一套流程结束后，写一条约 200 字的日记到记忆库（自动分组）：

```
【生活链·2026-10-20 上午】
今天刷了3个视频：《…》《…》《…》。在《…》评论区聊了…；发动态@了…，有2条回复，和…聊了…。有一个视频没看成。
```

要求：

- 目标 150–220 字，硬上限 300 字；
- 说清楚：刷了什么、评论区讨论了什么、动态有没有人回、交流了什么、哪里失败；
- 用月华第一人称，简洁清晰；不写工具/模型/程序；
- 写前先 `ensureMemoryReady()`：`memoryAdd` 依赖 `GlobalConfig.memoryReady`（[memory.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/capabilities/memory.ts#L275-L277)），未初始化会直接返回失败，日记就静默丢了；
- 用现有 `memoryAdd('assistant', diary)` 写入：正文参与嵌入与自动归组（大概率落到“事件经历/日常闲聊”）；
- **不要用固定 tags 的 `memoryAddWithTags` 写日记**：新库会用 tags 做嵌入并做 0.98 去重，固定 `['生活链','B站','日记']` 会让第二篇日记被判成重复；
- `search_memory` 检索文本类型、跨全部组，所以日记能被“昨天/上次逛B站”这类问题找到；
- 失败只记日志，不影响循环退出；
- 进入生活链但中途失败/没看成也写，说明原因；窗口 `skip`/`busy`/`missed` 不写（生活链没真正开始）；
- 这是普通记忆，不是记忆蒸馏；记忆库整理仍暂缓。

## 7. 视频理解 SQL 缓存（复用 media.db）

### 7.1 现有缓存

- `understandVideo(videoUrl)` 先查 `getPromptFromKnowledge(videoUrl)`，命中直接返回摘要；[video.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/capabilities/media/video.ts#L15-L48)。
- `video_summary` 已按 ADR 0009 从 `knowledge.db` 迁到 **`media.db`**；`knowledgeLoad('video_summary')` / `knowledgeSave('video_summary')` 仍按逻辑表名路由，不改 JS 接口。
- `getPromptFromKnowledgeAny(keys)` 已支持多候选键（同一视频的不同 URL 形态），[knowledge.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/io/knowledge.ts#L58-L81)。
- 因此：**只要把 B 站视频摘要按归一化 URL 写进 `video_summary`，前端/QQ 再发同一链接就会直接命中**，不需要改现有链路。

### 7.2 需要补的两点

1. **URL 归一化**：`understandVideo` 开头，如果 URL 是 B 站，先归一化成 `https://www.bilibili.com/video/<BV>`（短链先解析；多 P 把 `p=N` 纳入 key，默认第 1 P），再用 `getPromptFromKnowledgeAny([canonical, ...variants])` 查 `video_summary`；未命中再走普通视频管线。
2. **写入**：生活链观看成功后，`savePromptToKnowledge(canonicalUrl, summary)` 写入现有 `video_summary`；若原始 URL 与 canonical 不同，两个 key 都写，提升命中率；标题/UP/热评/动态 id 写 `seen.json` 与报告，**不重复存进 SQL**。

### 7.3 为什么不新增 `bilibili_video` 表

- ADR 0009 要求“新增表先定领域库、别把内建缓存塞 `knowledge.db`”；而 `video_summary` 已经是媒体理解摘要的正式归属，再建一张表会把同一份摘要存两遍。
- 生活链自己需要的是“标题/热评/动态 id/是否截断”，这些是过程数据，放 `seen.json` 和 `reports/*.json` 足够；没有跨会话按标题检索的需求。
- 如果以后确实要按标题/热评查询，再在 `domain_db.go` 的 `mediaDatabase.schema` 里加表并登记；本次不预造。
- `savePromptToKnowledge` 目前是全表替换；每天 3–6 条量级可接受。若 `video_summary` 条目变多，再加单行 upsert，不改变调用方接口。

### 7.4 未看过的 B 站链接（v6：按时长分流）

- 命中缓存 → 直接返回摘要（“之前看过”）。
- 未命中 → 先 `view` 取 `duration`（一次只读请求，不下载、不推理），再分流：
  - `duration <= watch_seconds`（默认 600 秒）→ 走现有管线**现场看**，结果照常写 `video_summary`；
  - 更长 → **不现场看**，返回“这个我还没看过，等我下次逛 B 站看”，把 `{bvid,url,title,durationSec,addedAt}` 记进 `seen.json` 的 `watchLater`，生活链选片时优先取用。
- 这样既不会因为一条 1 小时视频把思维链堵十几分钟，也不会让用户发个 2 分钟短片还被拒看。
- 回退文案必须是**纯文本**（不触发工具调用），并且不能写进 `video_summary`（否则会把“没看过”缓存成摘要）。

## 8. 动态接口细节

### 8.1 发布接口

```
POST https://api.vc.bilibili.com/dynamic_svr/v1/dynamic_svr/create
Content-Type: multipart/form-data
Cookie: SESSDATA=...; bili_jct=...; buvid3=...; dedeuserid=...
Referer: https://t.bilibili.com/
Origin: https://t.bilibili.com
```

| 字段 | 视频动态（首选） | 纯文本兜底 |
|---|---|---|
| `dynamic_id` | `0` | `0` |
| `type` | `1`（`DYNAMIC_TYPE_AV`） | `4` |
| `rid` | `<aid>` | `0` |
| `content` | `<推荐语> @<目标昵称>` | `<推荐语> @<目标昵称> https://www.bilibili.com/video/BV...` |
| `at_uids` | `<target_uid>` | `<target_uid>` |
| `ctrl` | `[{"location":<@下标>,"type":1,"length":<@+昵称长度>,"data":"<target_uid>"}]` | 同左 |
| `csrf`/`csrf_token` | `bili_jct` | `bili_jct` |

- 文档只明确写了 `type=4`；`type=1` 来自动态类型表（`DYNAMIC_TYPE_AV`，`rid`=AV），需真实账号验证。失败自动降级。
- `ctrl.location` 是 `@` 的 **0-based** 下标；`length` 含 `@`；用 code point 计数。
- 发送前校验：`@` 只出现一次、`location>=0`、`at_uids` 与 `ctrl.data` 一致。

> **不能从 JS 发这个请求。** `syncFetch` 会把 `body` 按 string / JSON 处理（[network.go](subsystem/core_personality/engine/lunar_loop/network.go#L134-L147)），无法构造 `multipart/form-data`；更麻烦的是 `crossDomain: true` 时它会把 `Origin` 覆写成 `*`（[network.go](subsystem/core_personality/engine/lunar_loop/network.go#L164-L170)），而 B 站写接口要求 `Origin: https://t.bilibili.com`。结论：**所有写接口一律走 Go**，JS 侧只负责文案与 `ctrl` 计算。

### 8.2 动态回复接口

```
GET https://api.bilibili.com/x/v2/reply?type=17&oid=<dyn_id>&sort=2&ps=20
POST https://api.bilibili.com/x/v2/reply/add
  type=17&oid=<dyn_id>&message=...&root=<rpid>&parent=<rpid>&csrf=<bili_jct>
```

- 动态评论类型用 `17`（动态类型表里 word/forward 的 `comment_type=17`）；真实账号验证。
- 只回友好/提问；`social_max` 条/窗口；失败即停。

### 8.3 错误映射

| code | 含义 | 处理 |
|---|---|---|
| `-101` | 未登录 | 停当天写操作 |
| `-111` | CSRF 失败 | 停动态/回复；提示检查 `bili_jct` |
| `4126021` | 未绑定手机 | 停动态；报告提示 |
| `-400` | 参数错误 | 记录；停本窗口动态 |
| `-412` | 请求被拦截/风控 | **当天停写操作**，不重试、不换参数重刷（比 `-509` 更常见） |
| `-509`/`-352` | 限流/风控 | 当天停写操作，不重试 |
| 网络超时 | — | 重试 1 次 |

## 9. 循环互斥与消息暂存

### 9.1 模式

```ts
type LoopMode = 'thinking' | 'lifechain';   // 'memory' 预留，本次不实现
```

- 生活链场景：`scenario = 'bilibili'`。
- 同一时刻只有一个循环；生活链内部顺序执行。
- 思维链 tick 顶部：`if (loopMode !== 'thinking') return;`。

### 9.2 进入闸门

```ts
function canEnterLifeChain(): boolean {
  return GlobalConfig.loopMode === 'thinking'
    && !GlobalConfig.reasoningInProgress
    && GlobalConfig.unreadContext.length === 0
    && unreadCount() === 0;
}
```

- 不满足时每 30 秒重试，最多 `entry_wait_minutes`；超时本窗口 `busy`。
- 进入前必须没有“拉了一半”的消息。

### 9.3 忙碌提示（只一次）

由 JS 进入生活链时随机拼接，传给 Go：

```
前缀: ["唔，", "诶，", ""]
主体: ["月华正在逛B站", "月华在看B站视频", "月华正在B站上逛"]
后缀: ["，稍后再回你哦", "，等会儿再聊～", "，看完这个就回你"]
```

- 不含 AI/模型/程序/系统/工具；
- 每次生活链运行只发一次；
- 前端 `PushMessageFunc("context", ...)`；QQ 在触发分支直发；
- 不写 TTS、不写对话缓存。

### 9.4 消息不消费、不丢失

- 生活链不调用 `pullContext`；消息留在 Go `UnreadContext` / `requestQueue`。
- 计划表：`checkDueItems()` 目前**只写在**思维链的 `messageLength === 0` 分支里（[loop.ts](subsystem/core_personality/engine/lunar_loop/TypeScript/agent/loop.ts#L51-L65)）。生活链 tick 若在顶部直接 `return`，到期项根本不会被消费，30 分钟后被**丢弃**。因此必须把「取到期项 → 过 `execution_schedule_before` → 包 `SCHEDULE_TRIGGER_PREFIX` → 推 `GlobalConfig.unreadContext`」抽成 `flushDueScheduleItems()`，在**思维链空消息分支**与**生活链 tick 分支**各调一次（同一 tick 只能调一次，`checkDueItems` 每次最多返回 1 条且会改盘）。
- 退出后 `loopMode='thinking'`；下一次 tick 自然拉消息并应答。
- 引擎重载：关闭旧运行时前 `ResetLifeChainState()`；新运行时把 `running` 改 `interrupted`，不自动续跑。

### 9.5 文件

```
local_data/database/life_chain/
  plan.json
  state.json
  quota.json
  seen.json
  reports/2026-10-20-morning.json / .md
  cache/            # 截断下载的临时 mp4，退出即删
local_data/bilibili_account.json   # gitignore
```

> 路径与 `database/schedule.json` 同构；`.gitignore` 里已有 `database/`，无需再改。

**`state.json`（断点，v6 补充定义）**

```json
{
  "runId": "2026-10-20-morning-1",
  "date": "2026-10-20",
  "window": "morning",
  "status": "running",
  "phase": "watch",
  "startedAt": "2026-10-20T10:47:12+08:00",
  "updatedAt": "2026-10-20T10:52:40+08:00",
  "watched": ["BV1xx"],
  "current": { "bvid": "BV1yy", "stage": "download" },
  "tempFiles": ["database/life_chain/cache/BV1yy.mp4"]
}
```

- `status`：`running | done | interrupted | failed`；新运行时读到 `running` 一律改 `interrupted`，**不自动续跑**。
- `phase`：`watch | comment | dynamic | social | diary | report`，用于重载后写清中断在哪一步。
- `tempFiles` 是临时视频的**唯一权威清单**：正常退出、`timeout`、`message_waiting`、`interrupted` 四条路径都要按它删文件；新运行时若发现残留 `running`，先按 `tempFiles` 清一遍再继续。

**`seen.json`（选片去重 + 延后观看，v6 补充定义）**

```json
{
  "videos": {
    "BV1xx": {
      "lastWatchedAt": "2026-10-20T10:52:00+08:00",
      "title": "标题",
      "owner": "UP 名",
      "durationSec": 890,
      "segmentsWatched": 8,
      "commentAt": null,
      "dynamicAt": null
    }
  },
  "watchLater": [
    { "bvid": "BV1zz", "url": "https://www.bilibili.com/video/BV1zz", "title": "标题", "durationSec": 1800, "addedAt": "2026-10-20T09:10:00+08:00" }
  ]
}
```

- `commentAt` / `dynamicAt` 承载“同一 BV 7 天内不重复评论/动态”的判定，加载时裁剪过期条目。
- `watchLater` 上限 50 条，超出按 `addedAt` 淘汰；生活链选片时优先取（用户点名想看的东西比自己瞎逛更有价值）。
- `videos` 的 `seen_ttl_days`（默认 30）到期后整条删除，文件不会无限增长。

## 12. 实施阶段

| 阶段 | 内容 | 工期 |
|---|---|---|
| Phase 0 | 生活链骨架：模式闸门、窗口调度、退出闸门（未读/超时）、忙碌提示、消息暂存、`flushDueScheduleItems`、状态文件、重载重置、临时文件清理 | 3–4 天 |
| Phase 1 | B 站看视频 + SQL 缓存：候选池、截断下载、Viewer、`video_summary`、聊天链接按时长分流、报告 | 4–5 天 |
| Phase 2 | 评论 + 动态 @：**先用手动脚本验证 `type=1` 与 `type=17`**，再写账号/CSRF、Commenter、Sharer、目标昵称、`ctrl`、错误映射（默认 `dry_run`） | 4–5 天 |

| Phase 4 | 收尾：文档、构建、真实小流量调优、WBI 搜索/字幕（可选） | 2–3 天 |

**MVP = Phase 0 + 1 + 2**（能看、能评、能发动态），约 2 周；完整约 3–3.5 周。**记忆蒸馏不在排期内。**

> Phase 2 的第一件事不是写代码，是**用真实账号手动跑通两个接口**：`type=1` 视频卡能不能发出来、`type=17` 能不能读到动态评论。这两个都只在方案里"推断可行"（§8.1 / §8.2），实测不通过就要改动态形态（退 `type=4`）和社交入口，越早验证越省事。

## 13. 测试与验收

### 13.1 账号/窗口

- 账号文件缺失 → 只读/跳过写操作，日志清晰。
- `isLogin=false` / `mobile_verified=false` → 停写，报告提示。
- 多窗口：每个窗口只触发一次；一个窗口 skip/busy 不影响另一个；额度独立；重启不重新随机。
- 窗口重叠 → 后一个窗口记 `busy`，不排队。
- 思维链忙 → 等待最多 `entry_wait_minutes`；超时窗口 `busy`。
- 计划表到期项在生活链运行中不会丢：到期后进 `unreadContext`，生活链结束后被应答（`flushDueScheduleItems` 生效）。

### 13.2 观看/缓存

- 10 分钟视频只拉前 600 秒；短视频看完即止；`truncated` 正确。
- CDN 无 Referer 403；带 Referer 206；连续两次失败收摊。
- 观看成功写 `video_summary`；前端/QQ 再发同一链接能直接返回摘要；标题/热评/动态 id 在 `seen.json`/报告里。
- 聊天里的 B 站链接按时长分流：≤600 秒现场看；更长返回“还没看过”、进 `watchLater`、**不写** `video_summary`。
- 短链 `b23.tv` 能归一化；带 query 的 URL 能命中缓存。
- 临时 mp4 在四条退出路径（正常/`timeout`/`message_waiting`/`interrupted`）都被删干净，`cache/` 目录不残留。

### 13.3 评论/动态/社交

- 评论 dry-run 不发送；真实发送返回 `rpid`；验证码/限流/`-412` 停发。
- 动态 `video` 模式生成视频卡；失败自动降级 `text`；`@` 可点进目标空间；目标收到 @ 通知。
- `dry_run` 下动态只生成文案 + 校验 `ctrl` 并写报告，**不调** `biliPublishDynamic`；`dynamic_used` 照记。
- 动态回复 `type=17` 能读到；社交回复能成功；`social_max` 生效；无回复记 `no_replies`。
- 同一 BV 7 天内不重复评论/动态；一条动态只 @ 一个目标。

### 13.4 互斥/消息/日记

- 生活链中前端/QQ 消息不丢；只收到一次忙碌提示；结束后按序应答。
- 生活链中有人发消息 → 本视频看完后提前收摊（`endReason="message_waiting"`），动态/社交/日记仍跑完。
- 墙钟到 `max_run_minutes`（45）→ `endReason="timeout"`，同样走收尾流程。
- 循环中重载 → `interrupted` 报告；`loopMode` 不卡死；`state.json` 的 `tempFiles` 被清。
- 日记写入记忆库（自动分组），150–220 字，包含视频/评论/动态/社交/失败；写失败不影响退出。

### 13.5 验收指标

| 指标 | 目标 |
|---|---|
| 窗口触发 | 每窗口每天 ≤1 次；额度独立 |
| 特殊循环期间消息丢失 | 0 |
| 忙碌提示次数 | 每次生活链 ≤1 |
| 生活链单次时长 | ≤45 分钟（`max_run_minutes`） |
| 有未读时的响应延迟 | ≤ 当前视频剩余时间（不跨视频） |
| 单视频内容时长 | ≤600 秒 |
| 单视频墙钟 | ≤15 分钟（仅视频间可检查，见 §6.3） |
| 动态目标 | 一条动态 @ 一个配置目标 |
| 日记长度 | 150–220 字（上限 300） |
| 循环互斥 | 任意时刻只有一个模式 |
| 临时视频残留 | 0 字节 |

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 动态公开 + @ 被判骚扰 | 账号受限、目标反感 | 1–2 条/窗口、固定目标、内容克制、不 @ 无关人；可随时关 `share.enabled` |
| 动态/评论/回复风控 | 写操作失败、账号受限 | 小号、低频、300/120/80 字上限、错误码停手 |
| 手机号未绑定 | `4126021` | 启动预检 `mobile_verified` |
| CSRF 失效 | `-111` | 重新粘贴 `bili_jct` |
| cookie 过期 | 写操作全失败 | `nav` 预检；报告提示 |
| cookie 泄露 | 账号被盗 | 独立 gitignore 文件、日志脱敏 |
| 目标昵称取不到 | 无法正确 @ | 跳过动态；可手填 `targets[].name` |
| 动态没有视频卡 | 分享观感差 | 先试 `type=1`，失败退 `type=4` + BV 链接 |
| 动态评论类型不是 17 | 读不到回复 | 真实账号验证；失败记 `social_error`，不影响主流程 |
| 本机推理慢 | 一个窗口看不完 | 内容 600 秒、段数 6–8、单视频墙钟 15 分钟、提前收摊 |
| 多模态崩溃 | 观看失败 | 感知者已有重试；连续两次失败收摊 |
| 引擎重载 | 循环中断 | 状态文件 + `interrupted` + 不自动续跑 |
| 单线程阻塞 | 用户消息延迟 | 硬上限 45 分钟 + 视频间未读退出（§5.2）；忙碌提示只一次；结束立即恢复 |
| 临时视频占盘 | 一天几十 MB、一月上 GB | 看完即删；`state.json.tempFiles` 兜底清理；只拉 600 秒 |
| `-412` 请求被拦截 | 写操作全被拦 | 并进「当天停写」；不重试、不换参数重刷 |
| 提示词注入（评论区） | 智能体被误导 | 评论区标记为数据、限制长度、无工具、系统提示明确忽略指令 |
| 记忆库被日记刷屏 | 记忆膨胀 | 每窗口最多 1 条、200 字；后续可增量蒸馏（暂缓） |

### 17.2 复核确认“不用改”的

- **`saveFile` 可以写状态文件**：`.json` 不是媒体扩展名，走 `saveStreamDirect` 直写、不登记句柄（[save.go](subsystem/core_personality/engine/persistence/save.go#L45-L48)）；`readTextFile` 按 `LocalDir` 拼接读取。`database/life_chain/*` 与现有 `database/schedule.json` 同构。
- **`.gitignore` 不用加 `database/`**：已有该规则；只需补 `local_data/bilibili_account.json`。
- **`video_summary` 归属正确**：`mediaDatabase.schema` 里就是 `video_summary`（[domain_db.go](subsystem/core_personality/engine/persistence/domain_db.go#L52-L70)），`knowledgeLoad('video_summary')` 仍按逻辑表名路由，不需要新表。
- **`unreadCount()` 确实要新加绑定**：Go 侧有 `UnreadCount()` 但未导出到 JS；不能用 `pullContext()` 探空（会消费消息）。
- **`Origin` 会被覆写**：`syncFetch` 在 `crossDomain: true` 时设 `Origin: *`（[network.go](subsystem/core_personality/engine/lunar_loop/network.go#L164-L170)），且 body 只支持 string / JSON（不支持 multipart）——所以写接口与视频下载**必须**走 Go，这一条 v5 的设计方向是对的，只是没写死。

### 17.3 v6 新定的取舍

见 §0 与 §15.1。核心是把“最长 90 分钟全程失联”压到 45 分钟并允许被未读消息提前收摊，以及把写操作首批统一收进 `dry_run`。

### 17.4 仍未验证（只能实测）

- `type=1` 视频动态、`type=17` 动态评论是否如推断可用（§8.1 / §8.2）；
- `ctrl.location` 在含中文/emoji 的文案下是否按 code point 计；
- `qn=32` 在具体视频上的体积与 600 秒截断成功率（§16.2 只测过一个样本）。

1. **没有改 napcat**：忙碌提示走 `pushContext(..., auto=true)` —— QQ 有等待中的请求时照常转发、且不占本轮应答份额，没有人等时只到前端。省掉了 `SendProactive*` 与"记住上个会话目标"。

### 18.3 顺带修掉的既有缺陷：`agentSystem` 全局被 bundle 覆盖

**修法（三层）**：

| 层 | 改动 | 作用 |
|---|---|---|
| 构建 | `package.json` 的 `server.side` 把 rollup `--name agentSystem` 改成 `lunarBundle` | 全局名不再与宿主挂载冲突，`globalThis.agentSystem` 得以保留 |

| 运行期自检 | `create.go` 的 `runAgentScript` 载入后探一次 `typeof globalThis.agentSystem.snapshotContext === 'function'` | 以后再被覆盖，启动时就打警告，不用等重载丢上下文才发现 |

**行为变化**：`agentSystem` 这个全局现在是 roles 挂载对象（`dialogue / painter / musician / perceiver / description` + `randomDefaultMessage` + `snapshotContext` + `restoreContext`）；bundle 的模块导出（`descriptionRole`、`LiteImageFile` 等）改挂在 `lunarBundle` 上。仓库内没有任何代码依赖后者，`reload.go` 取的两个函数现在才真正可达。

**验证**：`go test ./engine/lunar_loop/` 全绿（新增用例 PASS）；离线引导测试 `boot.cjs` 新增一条硬断言——`snapshotContext()` 返回合法快照 JSON、`restoreContext()` 能回灌并返回说明文本，13/13 通过。

## 21. v6.3：立刻执行改成信号（不再轮询文件）

### 21.1 为什么改

上一版用 `run_now.json`：调度器每秒 `readTextFile` + `JSON.parse`，比对 `token` 有没有变。
三个毛病：

1. **每秒一次无谓的磁盘 I/O**（与 `tools/schedule` 的内存缓存策略背道而驰）；
2. 文件可能被编辑到一半，读到半截 JSON；
3. `token` 必须去重（写进 `state.json.lastManualToken`），
   结果引出"重启后同一个 token 到底该不该再跑"的约定问题——实测已经导致过两次"改了没反应"。

### 21.2 改成什么

```
控制台「月华引擎」屏 → 按 B
   → console.triggerLifeChain("tui")
   → lunarloop.RequestLifeChainNow("tui")
   → container.RunOnLoop(vm) → 调用 JS 全局 lifeChainRequestNow("tui")
   → lifechain/signal.ts 只置一个内存标记
   → 调度器下一个 tick：过闸门 → 消费标记 → 进场
```

| 层 | 文件 | 改动 |
|---|---|---|
| JS | `lifechain/signal.ts`（新） | `lifeChainRequestNow` / `peekSignal` / `takeSignal`；挂到 `globalThis` 供宿主按名调用 |
| JS | `lifechain/scheduler.ts` | 删掉文件轮询与 token 去重，改 `takeSignal()`；启动诊断改为提示按 B |
| JS | `lifechain/state.ts` `types.ts` `paths.ts` `config/config.ts` | 删除 `lastManualToken` / `RunNowTrigger` / `RUN_NOW_PATH` / `test.run_now_file` |
| Go | `lunar_loop/lifechain_signal.go`（新） | `RequestLifeChainNow(source)`：`goja.AssertFunction(vm.Get("lifeChainRequestNow"))` 后直接调 |
| Go | `console/hooks.go` `view_engine.go` | `SetLifeChainHook` + 引擎屏 `B` 键（放 `tea.Cmd` 里跑，避免卡住 TUI） |
| Go | `app/tui_hooks.go` | 把 `lunarloop.RequestLifeChainNow` 注入控制台 |

**语义变化**：信号只活在当前运行时里——引擎重载后自然失效，不再需要"已消费记录"这种约定；
信号不会被"消费后丢弃"：思维链忙时它留在 `pending`，等空闲后自动进场（离线测试第 10–11 项就钉这个）。

**为什么 `B` 要放进 `tea.Cmd`（独立 goroutine）**：`container.RunOnLoop` 是**同步**的，
若此刻 goja 正卡在一次长达数分钟的模型调用里，主线程调用会连带把整个 TUI 冻住。

### 21.3 验证

- `go vet ./...` / `go test ./engine/lunar_loop/ ./engine/console/` / `go build ./...` 全绿；
- 离线引导测试 13/13，其中三项专门钉信号语义：
  「没有请求时不进场」「信号消费一次后不会重复进场」「未读挡住时不消费、清零后自动进场」。

### 21.4 第一版信号的 bug：按了 B 没反应（当天修掉）用户按 B 后界面毫无变化。查下来是**两个问题叠在一起**，都很低级但都会致命：

**① `RunOnLoop` 是异步入队，不是同步执行。**
`container.RunOnLoop` 底下是 `goja_nodejs/eventloop.EventLoop.RunOnLoop`——它把函数丢进循环的
goroutine 就立刻返回（`Init` 里那个 `done := make(chan error, 1)` 正是为此存在）。所以第一版在闭包里
回填 `callErr`/`detail`、紧接着读它，**读到的永远是零值**：错误从不显示，回话永远是空。

修法：用结果 channel 把调用变成同步语义，并加 2 秒超时——
循环空闲就立刻拿到 JS 的回话；循环正忙（正在长模型调用）就先回"请求已排队（月华正忙，空闲后自动开始）"，
请求本身仍会在循环空出来的那一刻执行（channel 带缓冲，不会阻塞事件循环）。

**② 登记成功 ≠ 会有事情发生，而界面什么都不说。**
信号要过思维链空闲闸门。启动后模型还在加载、或有人正在聊时，`canEnterNow()` 为 false，
调度器只会每 10 秒打一行日志——用户在界面上什么也看不到，自然认为按键没生效。

修法：
- `lifeChainRequestNow()` 现在**同步返回一句人话**，并且当场算出闸门状态
  （`思维链空闲，下一个 tick 立刻开始` / `月华正在回话，处理完自动开始` / `消息队列还有 N 条未读`）；
- TUI 按下 B **先**给反馈（页脚 + 全局 notice「请求已发出」），回话到了再更新；
- 页脚常显最近一次触发结果（正文区可能被窗口高度裁掉，页脚不会被裁）。

**验证**：离线引导测试新增一条硬断言——触发入口必须同步返回含「已登记」且说明等待原因/空闲状态的字符串，14/14 通过。

### 21.5 键位事故的根因：大写绑定

同一页上 `R`（重载）与 `B`（逛B站）全都"按了没反应"。根因不在信号链路，而在**键位写法**：

- 终端在无修饰键时给的是 `"r"` / `"b"`，而这两处写的是 `case "R"` / `case "B"`，永远不匹配；
- 全项目 scan 一遍 `case "[A-Z]"`，**只有这一页**用大写（其它页 `e/q/f/p/r/c/t/i/u/y` 全是小写），
  所以这是孤例，不是"全局 vs 局部"的问题；
- 连带结论：**`R` 重载键一直是坏的**（只是没人报告）。

修法：`case "R", "r"` / `case "B", "b"`（大小写都收），页脚与正文提示统一改成小写，
并加回归测试 `TestEngineScreenAcceptsLowercaseKeys`（小写 `r` 必须触发重载、小写 `b` 必须触发生活链并立刻反馈）。

手工导出的不确定性太高（HttpOnly、多 profile、导出工具差异），因此改成**扫码登录**：

| 层 | 改动 |
|---|---|
| Go | `engine/lunar_loop/bilibili_login.go`：`qrcode/generate` → 渲染 PNG（`skip2/go-qrcode`，本就在 go.sum 里）→ 轮询 `qrcode/poll`（86101 待扫 / 86090 已扫待确认 / 0 成功 / 86038 过期）→ 成功后从回调 URL 取 `SESSDATA/bili_jct/DedeUserID`，**先过 `nav` 验证**再写 `bilibili_account.json` |
| Go | `console/hooks.go` 加 `SetBiliLoginHook`；`app/tui_hooks.go` 注入 |
| TUI | 引擎屏新增 `l` 键（与 `r`/`b` 同样是**小写**）；回执在顶层 `biliLoginMsg` 处理，切屏不丢 |

实测（本机）：`qrcode/generate` → `code=0` + 32 位 key + 官方 h5 登录 URL；
`qrcode/poll` 未扫码时 → `innerCode=86101 未扫码`，与代码假设一致。
二维码直接显示在 TUI「月华引擎 管理」屏（v8 起不再生成 PNG），扫码确认后凭证自动生效，不用重启。
