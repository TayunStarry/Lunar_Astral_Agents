### 实现期修正的原始设计

1. **已落盘的本地文件不做规范化重命名**：原计划「统一落盘为 `multimedia/<sha16><ext>`」会让前端仍按旧 URL 引用的文件 404。实际实现为：已在仓库内者保留原地（必要时建规范名硬链接），目录表以实际存在的路径为准。
2. **共享 blob 的降级判定**：内容去重后多行句柄可能指向同一 blob，回收其中一行不得把其它行标记为 `lost`；只有实体确实不存在时才降级。
3. **强制回收的语义**：`force` 忽略配额但仍按等级顺序处理，且不承诺保护任何等级；配额模式才是「A 级永不动」的保证路径。
4. **搜索不使用 FTS5**：中文无空格分词在 `unicode61` 下不可用，改以子串匹配 + 段落标题补齐命中，规模（千级）与召回确定性更优。
5. **新增第五类来源 `workspace`（工作区文件）**：原文只定义了 path / url / data / bytes 四类，缺了「用户在对话里直接点名一个从未上传过的项目文件」（如 `@AGENTS.md`）这一实际场景 —— 原实现的自由文本引用只在资源目录里查同名条目，归档为空时引用静默失败。补充实现：`resolveWorkspaceSource` 以进程工作目录为根解析相对路径（含越界防护、文本扩展名白名单、100MB 体积上限），`placeWorkspaceBlob` 以硬链接优先、复制兜底的方式建立存档副本，**绝不移动或删除用户的项目文件**。

### 实现记录（问题与修复）

1. **引用按钮未渲染 / 引用未展开**：线上 `archive.db` 为空、`file_mapping` 表不存在，说明 `@AGENTS.md` 从未可解析。根因是自由文本引用只查资源目录，没有「按需收录」路径。已由上述第 5 项修正，并加回归测试 `TestArchiveWorkspaceRealFile`（用仓库根真实的 `AGENTS.md` 走完收录 → 整篇取回 → 章节锚点取回 → 原文件仍在）。

2. **goja 结构体字段名与 JSON 标签不一致（严重）**：适配器直接把 Go 结构体交给 goja，goja 按 **Go 字段名**（`Handle` / `ContentHash` / `BlobPath`）映射为 JS 属性，而 TypeScript 侧全部消费代码用的是 **json 标签名**（`handle` / `content_hash` / `blob_path`）。表现是一连串静默失败：句柄读出 `undefined`、段落表写入报 `FOREIGN KEY constraint failed`、引用展开拿不到正文。修复：新增 `toJS()` 做一次 JSON 往返，使 json 标签成为线上字段名的唯一来源。**这类缺陷只有跨到 JS 边界才会暴露** —— Go 侧单元测试全绿也照不出来，因此补了 `archive_bridge_test.go` 直接在 goja 运行时里断言字段名与往返结果。
   连带修正：`resourceAdmit` 增加入参完整性校验（缺 `sourceKind` 且无 `source`/`data` 一律拒绝），否则空对象会一路建表、写出 `kind="" / seq=0` 的垃圾目录行。

3. **同名不同路径的文件被反复收录**：旧的中文对话里连发两次 `build.ps1` 就产生了两条内容完全相同的目录行（`@D.001` 与 `@D.003` 的 `content_hash` 一致）。根因是索引只按句柄与`#文件名`存，没有「来源路径」键，于是每次引用都重走一遍收录流程。修复：索引增加 `@path:<来源路径>` 键与 `contentHash` 字段，`resolveFreeTextReference` 改为「路径索引 → 目录同名 → 按需收录 → 历史迁移」四级解析；同时资源名改用**引用时书写的相对路径**（`sub/build.ps1` 而非裸 `build.ps1`），让目录里同名文件可区分。

4. **文件引用按钮只出现在助手回执上**：用户气泡里的 `@D.003` / `@文件名.ext` 是裸文本。修复：`render.js` 新增 `fillUserMessageContent`，把引用标记渲染为可点击的行内按钮（复用既有 `.file-ref-inline` 样式）；`send.js` 不再把纯文件消息写成「已将文件 x 交给月华」（这会在服务端回执之外多留一个空气泡），改为留空正文 + `file` 类别徽标，由服务端回执承载该气泡。

5. **入库会把来源文件搬走（数据丢失，严重）**：`placeBlob` 的第三分支对仓库外来源调用 `moveFile`（先 rename，跨卷则复制后删除源文件），于是 LocalDir 内 `documents/` 等子目录下的原文件在导入后消失。修复：删除 `moveFile` 与专用的 `placeWorkspaceBlob`，统一为「**源文件一律原地保留**」——优先硬链接、失败则复制，只有系统自建的临时文件（下载件、字节流中转文件）按来源类型清理。补 `TestArchivePathSourceKeepsOriginal` 回归（断言源文件在原位、内容未改、二次入库仍不消失）。

6. **引用展开无条件注入全文**：无段落结构的资源走 `readResource` 整篇注入，大配置/日志被引用时会整篇灌进上下文；同时 `processReferencesInText` 在展开内容之后又追加一次「用户问题：…」，而该问句本来就在消息里，造成重复。修复：新增 `FULLTEXT_CHAR_LIMIT`（6000 字符）闸门 —— 小文件自动注入全文，大文件只注入资源卡片（标题/体积/节数/摘要）+ 取用提示，正文交由模型调 `read_resource`；问句改为原位保留，不再重复追加。有标题结构的文档本就按问题选段注入（预算 12000 字符），不受影响。

7. **归档副本混进媒体根目录**：早期实现把归档副本直接铺在 `multimedia/` 根下 —— 而该目录是图片/视频的**服务目录**，结果配置文件、源码快照都堆进了「媒体文件夹」；回收器也无法区分「归档副本」与「前端上传件」，存在误删前端原件的风险。修复：**归档副本按扩展名分类进两棵树**（媒体类 → `multimedia/`，其余 → `documents/`），归属改用资源目录的 `blob_owned` 列表达；回收器只处理 `blob_owned=1` 且未被任何 `blob_owned=0` 行引用的实体，删除前两道守卫。同时系统存储内已有的实体改为**直接引用、不复制**（前端上传的图片/文档不再产生第二份副本）。补 `TestArchiveOwnedBlobLayout`（分类落点 + 受保护实体回收后仍存活）与 `TestArchiveLocalPathNoCopy`（不得复制副本、不得标记为可回收）断言。
   > 中间曾用 `documents/archive/`、`multimedia/archive/` 子目录表达归属，后经评审废弃：路径前缀只是表达归属的手段，却给目录结构加了无谓嵌套、并把「文档的家」又切成两半。放进根目录 + 归属列更直白，且删除前本就必须查引用计数。

8. **`file://` + 相对路径取不到资源实体**：资源按句柄取用时，TS 侧拼出 `file://multimedia/<sha16>.jpg`，Go 侧去掉协议后交给 `os.ReadFile`，而该函数只接受绝对路径 → 读取失败。表现是绘制者拿到 `@I.001` 后 `select_reference_image` 报「该图源已失效」，**而实体其实完好躺在 multimedia/ 下**（资源目录、句柄、段落、描述全部正常，只有这一处取图链路断了）。
   修复分两步：
   - **TS 侧不再拼 `file://`**：进程内一律用**相对 LocalDir 的裸路径**。`file://` 是给 llama-server 媒体管线用的 URI 方案（其 `media-path` 指向 multimedia 根），不是本进程的路径格式；系统既有的文件读取端点也正是 `GET /file/read/<相对 LocalDir 路径>`（`ReadHandler` → `module.ReadFile`，内部按 LocalDir 解析），裸路径与它约定一致。改动点：`resourceSource()`、`resolveImageRef()`、`describe.resourceSource()`。
   - **Go 侧统一三级解析**：绝对路径 → 相对 LocalDir → 相对工作目录；`file://` 引用的文件**真不存在时明确报错**而不是回退成裸字节（否则调用方只能在几千字节乱码里猜原因）。保留 `file://` 入参分支以兼容既有调用方（llama-server 媒体引用走的是另一条路，不受影响）。
   补 `TestImagePipelineResolvesResourceBlob`（`file://`+相对路径、裸相对路径、缺失引用三类入参）。
   > 教训：**「句柄索引正确」与「正文可读」是两条独立的链路**。前者由 Go↔JS 桥接测试覆盖，后者只有真的把字节读出来才算通 —— 单测断言句柄与段落表全绿，也照不出这一层。另外：**不要为进程内传递另造 URI 方案**，系统已有的路径约定（相对 LocalDir）就够用。

9. **参考图措辞的「发送方/接收方」格式漂移**：调度方把「用户指定 @I.002 作为图生图基座，参考图已准备就绪：<path>」写进任务描述，绘制者用正则解析回来 —— 这是靠自然语言承载的**跨文件隐式契约**。句柄格式从 `[图片.002]` 改为 `@I.002` 时只有写入侧跟着改，解析正则仍匹配旧写法，于是 `referencePrepared` 恒为 false，图生图被判「参考图未在当前任务中正式选定」，模型只能向用户道歉、转而画自画像 —— **表面看是"基座未选定"，实际是两端字面量各自演化**。
   修复两层：
   - **格式收归唯一所有者**：措辞由绘制者侧提供 `PainterRole.referenceReadyNote(handle, path)` / `referenceUnreadableNote(handle)`，调度方调用它组装，不再自留字面量（`agent-control.ts` 里的两份硬编码文案已删除）。
   - **契约由测试对拍两端源码**：`engine/reference_format_test.go` 直接读两个 TS 文件，抽出正则并断言发送方措辞能被解析出路径，同时兼容历史 `[图片.NNN]` 写法、并禁止调度方再出现该措辞的可执行字面量。已用变异测试验证有效性（把正则改回旧写法 → 测试立即失败）。
   > 同批修掉一个下标 bug：正则改成单一捕获组后，解析处仍读 `match[2]`，即使匹配成功也会拿到 `undefined`。

10. **旧标签兼容层被彻底移除**：`图片.00x` 体系废弃后，代码里仍留着一批「为它留后路」的分支，全部删除：
    - `normalizeImageTag` 的 `图片.NNN` / 裸序号映射 → 现在只接受统一句柄，旧写法一律返回空串（无效输入）
    - `resolveImageRef` 的「历史句柄 → 热窗口缓存」分支 → 该分支早已恒不可达（句柄空间与缓存编号是两套东西），连同返回值里的 `handleKind` 字段一并删除
    - `TAG_ITEM_PATTERN` / `TAG_INLINE_PATTERN` / `isTaggedPlaceholder` 中的 `图片.NNN` 备选 → 只保留句柄形态
    - `list_images` 里「热缓存中有、目录中没有的历史条目」清单（两处）→ 清单只以资源目录为来源，热窗口仅用于标注 `[窗内]`
    - `evadeImageTags` 的「旧写法 → `@I.00x`」正向映射 → 函数删除，`extractMemoryText` 直接返回文本（句柄本就无需改写）
    - 绘制者正则中的 `[图片.NNN]` 备选 → 只接受 `@I.NNN` / `[@I.NNN]`；契约测试同步断言**旧写法必须被拒绝**
    > 顺带修掉三处因旧句柄空间残留而**静默失效**的调用：`dialogue.describeImage` 用统一句柄去查热窗口缓存（恒查不到，解钉与描述回写全部落空）、`painter.handleListImages` 列的是缓存内部编号而非模型可用句柄。当时改为「按来源定位缓存条目」，**随后连同整个缓存一起删除**（见下文「图片热缓存彻底移除」）。

### 图生图效果不达预期的定位（2026-10-17）

现场：`@I.003`（2:3 立绘）要求「沙滩改成森林」，链路全部跑通、91.6s 后出图，但画面仍是沙滩构图。

从引擎日志逐项对账，找到**三个独立问题**：

1. **适配器把边长读成了 0（真 bug）**：绘制者按参考图比例算出 `1024x1536` 并写入参数，而引擎日志是
   `尺寸归一化: 0x0 -> 1024x1024` —— 引擎收到的是 0，于是退回配置默认的方形 `sd_image_size`。
   根因：**goja 把 JS 整数导出为 `int64`、小数导出为 `float64`**（见 `goja_export_test.go` 实测），
   而 `generateImage` 只断言 `float64`，于是 `width` / `height` / `steps` / `batchSize` / `seed`
   全部静默变 0。后果有两层：输出从 2:3 变成 1:1（参考图被拉伸），以及所有"整数型"参数一律失效。
   修复：新增 `asInt` / `asFloat` 逐类型接受，`generateImage` 与 `narrator` 的配音参数、
   `container/fetch` 的 `timeout` 一并改过（后两处是同类潜在缺陷）。
2. **图生图的 cfg 给低了**：实测参数为 `--strength 0.70 --cfg-scale 1.00`。`--cfg-scale` 决定提示词
   对去噪方向的牵引力，而图生图的起点是参考图加噪后的潜变量、天然偏向原构图；cfg 过低时提示词
   拉不动画面，表现就是"强度给到 0.7 仍然只换色调"。文生图起点是纯噪声，低一点也能出图，
   因此**两边的 cfg 默认值不能共用**。修复：新增 `resolveImg2ImgCfg`（缺省 2.0、下限 1.5），
   并在 `painterRole.md` 给出 `2.0~3.0` 的图生图指引。
3. **`strength` 指引把"换服饰"与"换地点"混为一档**：原指引 `换场景、换服饰但保留主体 → 0.4~0.55`，
   绘制者据此选了 0.5。但换服饰/配色只需小幅偏离，换地点是整幅重构。修复：拆成两档
   （换服饰/配色 `0.4~0.55`；换背景/地点 `0.65~0.8`），并说明加噪机制与后果。

**仍未解决的能力上限**：上面三条都是参数层面。`--strength` 式图生图**没有遮罩**，整张图一起加噪，
因此"彻底换地点而人物不动"这类需求只有靠 **inpainting（`--inpaint-mask` 局部重绘）** 才能达成，
而本工程的封装尚未暴露该参数。这是方案层面的缺口，不是继续调参能补的。

顺带澄清两处易误解的实现：

- **`--llm_vision`（mmproj 视觉投影仪）与出图无关**：它只在图生图分支里挂给 `--llm`，
  服务的是**提示词理解**（文本侧多模态），让模型读懂 prompt 里的指代。
  图像条件走的是 `--init-img` → VAE 编码那条常规链路，扩散模型并不经过这个投影仪。
  因此"传了投影仪所以效果该更好"这个预期不成立。
- **`--hires-denoising-strength` 是无效参数**：sd.cpp 的二次采样需要 `--hires` 才会启用，
  而本工程从未传 `--hires`，那行参数只是让人误以为存在一次"高分辨率再扩散"。
  已删除该参数并注明：超分走 RealESRGAN 放大，不做二次去噪、构图不会再变。

### 图片资源的按内容去重（2026-10-17）

现象：同一张图被三次发送后占用了 `@I.002` / `@I.003` / `@I.004` 三条目录行，
且 `multimedia/` 下并存 `a22868fc9dec3e1b.png` 与 `a22868fc9dec3e1b.jpg` 两份同内容实体。

根因：入库层刻意「序号永不复用」，而**图片没有"文件名"这类业务身份**，此前只在
`@path:<来源>` 索引层面做去重 —— 前端每次重发同一张图时来源形态会变（base64 文本不同），
索引随即失效，于是每发一次就新增一条目录行。

修复：
- Go 侧新增 `resourceFindByHash(kind, hash)`（经 `resourceFindByHash` 暴露到 JS）
- TS 侧新增 `admitBytesDeduped`：入库前先算内容哈希（`hashBytes`）→ 命中则复用既有句柄
- 图片入口改用**压缩后的图片字节**入库（`admitImageData`），而不是原图地址：压缩字节稳定，
  内容哈希因此能稳定命中去重；`dialogue` 的 data URI 兜底路径同样先查哈希

已把线上那三条重复行合并为同一实体并删除多余副本（句柄保留，历史消息不受影响）。

### 事故复盘：`atob` 返回字符串导致入库图片全损（2026-10-17）

**症状**：用户指定 `@I.006` 做主图，绘制者却去画了 `@I.001`。日志里真正的第一因是：

```
10:31:58  ResizeImage: 检测到原始格式=unknown
10:31:58  ResizeImage: FFmpeg转码失败: exit status 0xbebbb1b7
10:31:58  调度绘制者（图生图）: …（用户指定 @I.006 作为基座，但该图源已无法读取…）
```

**根因**：为做「按内容哈希去重」，图片入库一度改成「JS 侧 `atob` 解码 base64 → 把字节传给 Go」。
而 `atob` 适配器的实现是：

```go
decoded, _ := base64.StdEncoding.DecodeString(input)
return class.runtime.ToValue(string(decoded))   // Go 字符串
```

goja 把该 Go 字符串按 UTF-8 解释成 JS 字符串，**所有非法 UTF-8 字节被逐个替换为 U+FFFD**；
JS 侧再 `charCodeAt(i)` 取回时，U+FFFD 的低字节正是 **0xFD**。于是入库的实体成了
「45% 字节是 0xFD」的垃圾（187KB 文件、PNG 头都没了），尺寸探测、解码、参考图准备全部失败。
两张受影响的图（`@I.005` / `@I.006`）内容不可逆丢失。

**修复（结构性，不是打补丁）**：
- **JS 侧彻底不碰图片二进制**：删除 `decodeBase64ToBytes` / `extractBase64Payload` / `admitBytesDeduped`，
  新增 `admitImageDataURI` 直接提交 data URI，**解码与哈希全部在入库层（Go）完成**。
- **按内容去重下沉到 Go**：`AdmitInput.Dedup` + `ResourceAdmit` 在算完哈希后查目录，
  命中则复用既有句柄、不落盘、不新增目录行。去重不再需要 JS 侧先算哈希。
- `dialogue` 的 data URI 兜底同样改为 `dedup: true`，删除其私有 `decodeBase64`。

**回归测试**（`archive_bridge_test.go`）：
- `TestResourceAdmitDataURIRoundTripsBytes`：PNG 以 data URI 入库后，**磁盘实体必须与原图逐字节相等**，
  不一致时报出首个差异偏移。这条测试直接钉死「谁在 JS 侧解码二进制」。
- `TestResourceAdmitDedupReusesHandle`：同一内容两次入库必须得到**同一个句柄**。

**数据修复**：`@I.005` / `@I.006` 保留目录行（序号按 `MAX(seq)` 分配，删掉最大行会导致**序号复用**），
删除垃圾实体、置 `state=lost`、写入「入库时损坏，请重新发送原图」摘要。
全量扫描确认仓库内仅这两张受影响，其余实体完好。

> **教训**：`atob` 的语义是「返回二进制字符串」，跨运行时桥接时**它不承载二进制**。
> 任何需要真实字节的链路，都必须让字节在同一个运行时内产生与消费。
> 另外：**「文件存在」不等于「文件可用」** —— 句柄、路径、实体三者都正常，
> 内容仍可能是垃圾；判断资源可用性必须校验内容本身。

### 图生图「换主体」的实测结论（2026-10-17）

现场：把「少女骑北极熊」里的北极熊换成熊猫，结果画面里**只剩一只熊猫，少女消失**。

先排除误判：`--init-img` 正确指向参考图、句柄解析与落盘都正常。问题在提示词与强度的配合。
参考图 = `7c47cf8cb0e345f6.jpg`（768×1024，Q版雪国女王骑白熊，星空冰山），
同 seed / cfg 2.5 / 40 步 / `-W 960 -H 1280`（比例一致，无裁剪）：

| 强度 | 提示词 | 结果 |
|---|---|---|
| 0.85 | **只写熊猫**（`a cute panda sitting in the snowy environment`） | 熊猫 ✅ / **少女消失** |
| 0.65 | 完整（女王 + 熊猫 + 场景） | 仍是北极熊 ❌ / 女王 ✅ |
| 0.75 | 完整 | 仍是北极熊 ❌ / 女王 ✅ |
| **0.85** | **完整** | **熊猫 ✅ / 女王 ✅** |

两条结论，都很反直觉：

1. **「想保住更多就调低强度」是错的**：画面里的大物体（坐骑、道具）其形状由提示词在去噪前段决定，
   `0.65` / `0.75` 下**要改的东西也改不动**。换主体与换场景一样需要 `0.8~0.9`。
2. **强度 ≥0.8 时提示词主导画面，没写进提示词的东西会消失**。所以「换主体」的真正难点不是强度，
   而是**提示词必须描述改完之后的整个画面**（含所有要保留的主体），而不是只写要改的那一处。

据此落地：
- `painterRole.md` 新增「替换画面里的一个对象 → 0.8~0.9」档位，并加了整节
  「图生图的提示词必须写『整个画面』」；工具参数说明同步。
- **修掉一个让绘制者「盲写提示词」的根因**：绘制者看不到参考图，此前连描述都没有。
  `dispatch_painter` 现在会在派发前确保参考图有内容描述（缺失则现场生成并回写目录），
  并以「参考图内容：…」随任务下发；`PainterRole.referenceReadyNote` 直接要求
  「提示词必须描述整个画面，把画中已有且需保留的主体一并写进去」。
- **顺带修掉 `describeResource` 取不到图的老问题**：它把「相对 LocalDir 的裸路径」塞进
  `image_url.url`，而推理服务不认这种形态，导致**库里所有图片摘要一直是空的**。
  现改为经 `readResource` 取 base64 拼成 data URI（与窗口内看图同一条通道），
  并对「被截断的二进制」直接判空，避免把半个文件当图片送进去。

> 教训：图生图的 **强度只决定「改多少」，提示词决定「改成什么」**。
> 而「只描述要改的东西」是写提示词时最容易犯、后果最重的错误 ——
> 在需要高强度的任务里，漏写的对象就是被删掉的对象。

### 绘制者在图生图前必须亲自看图（2026-10-17）

上一节证明：图生图失败的根因是**提示词只描述了要改的东西**。而漏写保留项之所以必然发生，
是因为**绘制者从来没见过参考图** —— 它只有一个文件路径和对话者的一句话。

成本上没有犹豫的余地：实测一次图生图 `150~240s`，而让多模态模型看一眼参考图只是秒级。

落地方式（不改工具、不改外部契约，只改绘制者的任务入注）：

| 位置 | 改动 |
|---|---|
| `CreativeRoleBase` | 新增 `buildTaskContent(taskDescription)` 钩子，任务消息内容可由子类覆写（默认纯文本） |
| `PainterRole` | 覆写该钩子：参考图存在时，把**图本体**（data URI）作为 `image_url` 内容项附在任务消息里，并附「看图要求」四条（列出必须保留的主体 / 按新对象实际样子描述 / 提示词要覆盖整个画面 / 负面点名旧对象） |
| `PainterRole.REFERENCE_READY_PATTERN` | 重新捕获句柄（组 1）+ 路径（组 2）；路径捕获从 `[^，）]+` 收紧为 `[^，；）]+`，否则会把「；参考图内容：…」一起吞进去、`referenceImage` 变成无效路径 |
| `PainterRole.dropHistoricalReferenceImages` | 每任务开工前清掉历史消息里的图片项（只留文字）：历史会随每次 `run()` 整体重发，累积旧参考图会成倍抬高 prefill；参考图本就是任务级状态 |
| `agent-control.ts` | 参考图描述改为**只读已有摘要、不再现场生成** —— 模型已能亲眼看图，为它多跑一次视觉模型没有意义 |

图片本体走 `readResource(handle)` 取 base64（Go 侧编码）拼 data URI，JS 侧不接触二进制；
被截断的二进制直接判空，避免把半个文件当图片送进去。

> 立刻失败，并顺带暴露了「路径捕获吞掉描述」这个会导致参考图再次失效的 bug。
> 再次说明：**「发送方格式化、接收方正则解析」这类隐式契约必须有测试对拍两端源码。**

### 图片标签机制收敛为「入队赋签 + 20 张窗口」（2026-10-17）

上一节的「发送方格式化、接收方正则解析」契约连同它的测试，已在本次重构中**整体废除** ——
正确的解法不是给隐式契约加测试，而是让跨端传递不再依赖自然语言。图片标签机制收敛为两条规矩：

1. **入队赋签**：消息推入未读数组时（`loop.ts` 的 `writeMessage`），为其中每个图片项

   （`image-tag.ts` 的 `attachImageTags`）。旁注从此是消息内容的固有组成部分，
   压缩、写入上下文、降级都只是搬运。
2. **窗口降级**：对话者上下文只保留最新 20 张真实图片；更早的图片项连同相邻旁注
   按位置置换为一条「[@I.00x]（描述）」文本（描述取目录摘要，缺失时视觉模型现场生成并回写）。

| 位置 | 处理 |
|---|---|

### 思维链图片统一为「视觉读取副本」（2026-10-17 第二批）

在「入队赋签 + 20 张窗口」之后，思维链中的图片流转形态进一步收敛 ——
无论来源是 HTTP(S) URL 还是 base64 data URI，静态图入库后**统一以视觉读取副本流转**：

1. **端点**：`GET /file/read-multimodal/<blob相对路径>?tag=<句柄>&size=<边长>`
   （`server/vision.go` → `engine.VisionReadBlob`）。仅允许 `multimedia/` 下的图片类文件；
   返回**派生副本**而非原数据：长边不超过 `agent.vision_max_side`（默认 1080），
   右上角叠印句柄标签（basicfont 白字黑底药丸），按「内容哈希 + 边长」盘上缓存
   （`multimedia/vision/`，簿记在 archive.db 的 `vision_cache` 表）。
2. **动图直通**：端点检测到 GIF / APNG / 动态 WebP 时原样返回（不缩放不叠印不缓存）——
   缩放会把动图坍缩成单帧，下游 `isAnimatedImage` 判定将永远失效。
3. **句柄随图走**：副本右上角烙印句柄 + URL 自带 `tag` 参数。旧「图片项后紧跟旁注文本」
   排布废除 —— 连续多图场景下相邻文本可能被模型对应到错误的图片上；
   现在模型看到的每张图自带身份，降级占位的句柄直接从 URL 解析（`handleFromVisionURL`）。
4. **原图不可变**：绘画者参考图（`initImg` 直读 blob 路径）与 `readResource` 取原图的
   链路拿到的数据**不带标签** —— 叠印只发生在派生副本上。
5. **双形态配置**：`agent.image_input`（`url` 默认 / `base64`）与 `agent.vision_max_side`。
   base64 形态经同一变换管线直出 data URI（`visionRead` goja 绑定），
   供无法回取本机 URL 的云端多模态服务使用 —— 与 `agent.video_input` 的 file/frames
   双模式同构。
6. **载荷收益**：思维链中不再流转 base64 图片本体（url 形态），20 张窗口的每次请求
   载荷从数 MB 降到 KB 级；缩放缓存命中后重复读取零变换开销。

对应删除：`LiteImageFile` 的静态图 `resizeImage` 分支与 data URI 透传分支（尺寸约束
收敛到端点单一卡口，修复「data URI 原样透传、约束靠上游自觉」的漏洞）。

2. `multimedia/6fdb179bcac7cf04.json` 的首行是 `{"models": {...` → 正是那份配置，**被搬到了媒体根**
3. 根因即上述第 5 项（`moveFile`）。已按第 5 项修复，并把该实体复制回 `documents/<hash>.json`（复制而非移动，归档副本保留）

**副带发现**：同一份内容被反复收录时，早期实现每次都把源文件搬到**同一个**规范名路径，导致先前的归档副本被**覆盖**（表现为目录行自相矛盾：一行显示文件存在、另一行显示同一路径不存在）。这正是第 6 项（按路径索引去重）必须存在的原因 —— 它从源头阻止了重复收录。

## 背景

月华在对话中需要稳定引用两类内容：图片与文本文件。当前实现是两套彼此独立、且各自都有半个洞的系统。

### 现状事实（代码实测）

| 维度 | 图片 | 文本文件 |
|------|------|----------|
| 句柄形态 | `[图片.003]`（可带 `（描述）`） | `#文件名.ext`，正文写 `(#文件名.ext):` |
| 权威存储 | 进程内 map（`imagecache`，容量 80 / 钉住 30），**只存 `Source` 字符串** | 切片逐片写入记忆库向量集合 `file_<sha16>` |
| 命名空间 | 隐式全局单调号 | 显式文件名句柄 |
| 生命周期 | 运行期，重启即失效 | 内容哈希集合永久驻留，**无删除路径** |
| 识别符号 | `[` … `]` | `#` + `(` `)` + 冒号 |

由此产生四个结构性问题：

1. **两套文法**：模型必须学两种引用风格，且各自都有边界问题（图片号重启重排、文件名寻址同名不同内容会复用同一 key）。
2. **寿命错配**：图片连字节都不落盘（`Source` 可能是 `data:` 内联串，全在内存），而文档切片永久驻留且无人回收。同一份"资料"在两端得到相反待遇。
3. **资源消耗**：一次文件导入的开销 ≈ 切片数 ×（1 次 embedding + 1 次向量写）+ 1 次知识库全表读改写；每次引用再 +1 次 embedding + 向量查询。3000 行文件即 30+ 次嵌入调用。
4. **切片是存储单位而非呈现单位**：结构前缀被当作正文写入向量库，检索回来靠 `---` 硬拼 —— 切片体验差的根因在此，不在分片算法。

### 数据来源现状（本次新增的关键约束）

同一张图片会以三种互不相容的形态进入系统：

| 来源 | 是否落盘 | 命名方案 | 代码位置 |
|------|----------|----------|----------|
| 前端上传（桌面/移动） | 是，`local_data/multimedia/<hash16>.<ext>` | SHA-256 前 16 位 | `hierarchy/assets/client/js/file-upload.js` |
| QQ 适配器等渠道 | **否，仅 URL** | 无 | `.../lunar/bridging/napcat/` |
| 工具产出（截图 / 绘图 / 超分） | 是，`multimedia/generated/`、`multimedia/moment/` | 时间戳或引擎自定 | `multimodal_analysis/module/generate.go`、`crystal/agent/AutoLTP/trace.go` |
| 视频 / 动态图本地化 | 是，`multimedia/footage/` | **SHA-1 前 40 位（对 URL 取哈希，非内容哈希）** | `multimodal_analysis/module/video_media.go` |
| 历史遗留 | 是 | base64 文件名（crypto 失败回退） | — |

即：同一图片在不同来源下有四种身份方案，且 `footage/` 用的是**对 URL 而非内容取哈希**，物理上相同的视频换一个 URL 就会重复落盘。这正是必须建立统一入口的实证，而不只是设计洁癖。

## 决策

### 1. 统一句柄文法

所有可引用资源使用同一文法，仅类型码区分场景：

```text
resource-handle := "@" typecode "." seq3 [ anchor ]
typecode        := "D" | "I" | "V" | "A" | "T"
seq3            := 3 位以上十进制序号，不足补零，不设上限
anchor          := "|§" section-index | "|L" line-start "-" line-end

示例：@D.003   @I.007   @D.003|§4   @D.003|L120-168   @V.001|L0-60
```

- 类型码：`D` 文档 / `I` 图片 / `V` 视频 / `A` 音频 / `T` 表格。新增资源类型只扩类型码，文法不变。
- 锚点仅用于段落级引用，**不构成第二套标识**：索引单元（大纲、段落表）不进句柄文法，只进目录表；句柄始终可解析。
- 实现约定：**正则在 Go 侧定义一处，经 goja 暴露给 TypeScript，前端由服务端下发校验**，禁止各处自写正则（现状 `image-recall.ts`、`reader.ts`、`websocket.js`、`dialogueRole.md` 各有一套）。
- 废弃形态按机械映射迁移：`图片.NNN` → `@I.NNN`，`#name.ext` → 该资源的 `@D.NNN`。

### 2. 双身份：序号与内容哈希

- **序号（`@I.007`）**：资源的人类可读名。首次入库时分配，**持久化且永不复用**；启动时从目录表重建计数，不重置。
- **内容哈希（sha16，小写十六进制）**：资源的存档身份。统一取 **SHA-256 前 16 位**（与前端既有约定一致），定义域为**内容字节**，非来源地址。用于去重、搬迁与目录重建。
- 两者关系：序号是主键，哈希是可在目录丢失后恢复引用的锚。同一内容多次入库 → 目录多行序号、blob 只存一份。
- 废止 `imagecache` 的"运行期有效"语义：`@I.007` 重启后仍可解析（附图或降级为描述）。

### 3. 三次分层职责

| 层 | 存储 | 保存 | 明确不保存 |
|----|------|------|------------|
| 资源目录 | SQLite `local_data/database/archive.db` | 句柄、类型码、sha16、物理路径、尺寸、来源、描述、创建时间、保留等级 | 不存正文、不存向量 |
| 内容仓库 | 文件系统（见下） | 资源原始字节（文档 / 图片 / 视频 / 音频） | 不做切片、不做结构化 |
| 记忆库 | 现有向量库 `local_data/database/memory/` | 会话回合（经历）+ **每资源一条**卡片向量 | **不再存文档切片** |

内容仓库布局：**分类沿用仓库既有的两棵树**（文档一棵、媒体一棵），归档副本与前端写入件同目录、同命名方案；归属记录在资源目录的 `blob_owned` 列上，GC 按目录行回收：

```text
local_data/documents/                  ← 文档存储（代码 / 脚本 / 文档 / 配置）
local_data/documents/<sha16>.<ext>     ← 前端保存的文本类文件 + 归档副本（同目录、同命名）

local_data/multimedia/                 ← 媒体存储根（llama-server 的 media-path）
local_data/multimedia/<sha16>.<ext>    ← 前端上传件 + 归档副本（同目录、同命名）
local_data/multimedia/generated/       ← 绘图 / 超分产出
local_data/multimedia/moment/          ← 自动截图
local_data/multimedia/footage/         ← 视频与动态图本地化片段
```

> **分类规则**：按扩展名判定 —— 图片/视频/音频进媒体树，其余进文档树。这与仓库既有分工
> （前端 `file-upload.js` 本就是「media → `multimedia/`，其余 → `documents/`」）完全一致，
> 不再另造分类、也不额外加一层目录。
>
> **归属不用路径表达，用 `blob_owned` 列**：
> - `blob_owned = 1`：归档自己写入的副本，配额回收可清理
> - `blob_owned = 0`：前端/引擎写入的实体，回收器**永远不删**（受保护）
>
> 为什么不用 `archive/` 子目录来区分（曾这样实现过，已废弃）：路径前缀只是表达归属的一种手段，
> 却给目录结构加了一层无谓嵌套，并让「文档的家」看起来又被切成两半。放进根目录后结构直白，
> 代价是删除前要多查一次归属与引用计数 —— 而**引用计数本来就必须查**，所以边际成本很小。
>
> **两道守卫**保证「回收器删不到用户可见文件」：
> 1. `blob_owned = 0` 的行直接跳过（前端上传件、引擎产出）
> 2. 即便某行 `blob_owned = 1`，只要**同实体被任何 `blob_owned = 0` 的行引用**（内容寻址下同内容共用实体），也一律不删 —— 归属按最保守的一侧处理
>
> 另外：媒体类归档副本必须落在 `multimedia/` 内 → llama-server 的 `media-path` 指向该根，
> `file://` 取用依赖它，同卷才能硬链接；前端已按 sha256 命名的实体**直接引用、不复制**。

记忆库写入规则：
- 文本资源：归档只存正文，**不产生向量节点**（或至多 1 条摘要卡片向量）；跨文档检索由目录表的标题/摘要全文索引承担。
- 图片资源：不写向量，靠目录表标签检索（今日 `stickers` 集合那种"图片进向量库"路径仅保留给表情包这类确有语义检索需求的集合）。
- 文档切片彻底退出向量库。检索的语义从"相似度拼接碎片"变为"目录定位 + 整段展开"。

### 4. 统一入库入口

新增单一准入层（Go 侧，置于 `file_manager/module/` 供三方共用，经 `create.go` 暴露到 goja 全局）：

```text
resourceAdmit(input) -> { handle, sha16, path, mime, bytes, deduped } | error
input.sourceKind  := "path" | "url" | "data" | "bytes"
input.origin      := "client-upload" | "channel" | "tool-output" | "engine-temp"
input.kindHint    := 可选类型码
input.retention   := "A" | "B" | "C"
```

准入层行为（三类来源归一）：

1. **已经是本地文件**（`path` 且落在 `multimedia/` 下，前端已落盘）：流式 SHA-256 取前 16 位 → 写目录表，**不复制不移动**，`path` 记录既有位置。若既有文件名与 sha16 不一致（历史遗留 / 引擎命名），在目录表登记为别名，不重命名。
2. **远程 URL**（QQ 等渠道）：下载到临时文件 → 计算内容哈希 → 落盘为 `multimedia/<sha16>.<ext>`（与前端同一命名方案，前端已有文件命中同一哈希则复用）→ 写目录表。
3. **字节流 / data URI**（工具产出、转发内联）：同上第三分支，落盘后登记。

约束：
- 准入层是**唯一**允许分配句柄与写目录表的地方；`imagecache.Put`、`reader.importFileBlock`、`video_media.go` 的命名逻辑全部收敛到此处。
- `footage/` 改以内容哈希命名（不再对 URL 取哈希），同一视频换 URL 不再重复落盘。
- 类型码与保留等级允许调用方给建议值，最终以准入层判定为准（按 MIME + 扩展名 + 来源）。

### 5. 保留策略与降级语义

| 等级 | 判定 | blob | 目录行与句柄 |
|------|------|------|--------------|
| A 必存 | 用户主动上传的图片、用户导入的文档 | 永久保留 | 永久 |
| B 产出 | AI 绘图 / 截图 / 超分结果 | 仅保留最新 + 被显式引用过的 | 永久；blob 回收后降级为描述 |
| C 参考 | 视频抽帧、GIF 中间帧、临时裁剪 | 不进入内容仓库 | 仅元数据，句柄标 `ephemeral` |

- 配额（起步值，可配置）：内容仓库总量 2 GB，单资源上限 20 MB；按 **等级 → LRU** 顺序回收。
- **回收只删 blob，保留目录行**：`content_state` 置为 `lost`，`@I.007` / `@D.003` 仍可解析，此时首次取用会生成或返回描述（图片）或大纲（文档）。句柄不再因超窗 / 淘汰而失效 —— 这是与现状最关键的语义差异。
- 目录行仅由用户显式删除或卸载时移除。

### 6. 记忆库存经历，资源库存资料

- **资源归档**：只收"谁提供的资料"（用户上传的图片、导入的文档、被引用的工具产出）。
- **记忆库**：只收"经历"（回合、月华的话、工具往返），以时间线 / 摘要形态存在，不再混入文档切片。
- AI 生成的图片归 B 级产出，不属于记忆；仅在被引用时具备留存价值。

### 7. 模型可见工具收敛

图片与文档合并为同一套操作（替代今日 `list_images` / `describe_images` + 隐式文件引用）：

```text
list_resources(kind?, limit?)   → 句柄 + 类型 + 标题/描述 + 内容状态 + 窗内标记
outline(@D.003)                 → 目录树 + 每节 @D.003|§n / |L120-168 + 字数
read(@D.003|§4 | @I.007)        → 段落原文 / 图片本体或描述
search_resources(query)         → 跨资源路由（定位到哪份资源、哪一节），再由 read 取正文
```

命中路径：**结构定位 → 整段展开**，不再有"相似度 topK 拼接"。半句截断与碎片拼接由段落边界保证消除。

## 结果

### 正面

- 模型只需一套引用文法，类型码区分场景；新增资源类型零文法成本。
- 一次文件导入的嵌入成本从 `O(切片数)` 降到 `O(1)`（或 0），引用时零嵌入调用。
- 引用结果连贯可复现：定位到结构单元再整段展开。
- 图片与文档获得同一套寿命语义（同句柄、同降级、同回收），QQ 渠道图片与本地图片行为一致。
- 同一内容只存一份：前端上传、渠道下载、工具产出在准入层按内容哈希天然合并。
- 句柄重启后可复活，长期引用不再被迫退化为纯文字描述。

### 负面 / 代价

- **跨文档模糊主题检索变弱**：向量只到资源卡片粒度。以 `search_resources` 路由 + `read` 取正文作为补偿。
- 需新增 SQLite 目录表与 GC 模块，并维护与 `archive.db` 的一致性（blob 丢失只影响内容状态，不影响句柄）。
- 迁移工作量：旧 `file_mapping` 与 `file_<hash>` 集合需一次性反演重建；前端通知与引用条需改渲染。
- `multimedia/` 继续承担 blob 仓库角色，命名不再承载语义（依赖目录表），对人工翻目录排查不友好。

## 迁移路径

1. **新增 `archive.db` 与准入层**，不改既有写入侧；对新增资源双写（旧 `imagecache` + 新目录表），保证可回退。
2. **反演旧文档集合**：逐 `file_<hash>` 读取切片，按 `*标题> 路径*` 前缀重建章节标题与层级（前缀本身即结构信息，正文完整保留），写为整篇资源 + 段落表；重建结果标记 `migrated_by=reconstruct` 以便人工抽检。
3. **旧 `file_mapping` 保留只读**，不再写入；确认无回归后移除读取路径。
4. **`imagecache` 缩为热窗口专用**：只负责"窗口内可直看"的集合与钉住，句柄与描述来源改为目录表；`FormatTag` 退役。
5. **前端改造**：文本文件不预构造引用，改为发送标记，由服务端在收录后回推 `[已收录] @D.003 文件名.md`，前端据此渲染引用条；图片标签展示改读目录表。
6. **文档同步**：重写 `docs/code-wiki/14-图片标签与多模态窗口.md`，并更新 `02` / `04` / `08` 中的交叉引用。

## 遗留问题（实现前需确认或先修）

1. `reader.ts` 的变更判定 bug：`message.content = ref.text` 先于 `res.text !== message.content` 比较，导致 `changed` 恒为假。本次重构顺带修正或直接删除该分支。
2. `multimedia/` 根目录当前平铺近 1000 个文件，且与 `background/` `icon/` `placeholder/` 等功能目录混放。新代码禁止在根目录新增非资源文件，既有目录保持不动。
3. `reader.ts` 中的文件围栏解析（`looksLikeFileHeader`）需同步：围栏首行由"纯文件名"扩展为可带保留等级标记，或改为不在前端构造围栏。
4. 目录表与知识库 `knowledge.db` 的边界：`file_mapping` 语义并入资源目录后，`knowledge.db` 只保留 `video_summary` 等媒体理解缓存。
5. 视频 / 音频是否纳入本轮句柄统一（类型码已预留 `V` / `A`，但准入层与工具是否同期实现需按施工顺序定）。
