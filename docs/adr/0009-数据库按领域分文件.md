# 0009 数据库按领域分文件

- 状态：已采纳
- 日期：2026-10-20
- 相关：ADR 0001 统一资源寻址与三层存储（代码注释引用，见 `archive_type.go`）

## 背景

SQLite 的使用一度没有清晰边界：媒体理解摘要、网页摘要缓存、自定义角色库、文件索引都塞在 `knowledge.db`，视觉副本簿记塞在资源名录库 `archive.db`，而同一个业务又跨两个库读写。结果是「相关表不在一个库、一个库装着不相关的事」，迁移、备份与排障都要同时盯着多个文件。

## 决策

按**数据所有者与生命周期**把 SQLite 拆成领域库，一个领域一个文件、一个连接；一张表只属于一个库。

| 库文件 | 领域 | 表 | 写入方 |
|--------|------|----|--------|
| `knowledge.db` | 通用知识库：用户 / 插件自建结构化数据 | 无内建表 | `/knowledge/`、LTP9 `database.*` |
| `archive.db` | 统一资源名录：句柄、元数据、文档段落结构 | `resources`、`resource_sections` | 资源归档层 |
| `media.db` | 媒体派生数据：动图/视频/音频理解摘要、视觉副本簿记 | `video_summary`、`vision_cache` | 月华感知链路、`/file/miniature` |
| `web.db` | 网络检索缓存：页面摘要 | `web_ltp_page_cache` | Web-LTP |
| `text.db` | 文本内容索引：文件标识 → 分块集合 | `file_mapping` | 阅读/索引链路（当前暂停） |
| `character.db` | 自定义角色库：绘图角色档案 | `painter_characters` | 绘制者角色 |

### 为什么资源名录不按媒体类型再拆

`resources` 同时登记 `@D` / `@I` / `@V` / `@A` / `@T`，但句柄序号按类型码分配、行 ID 是单库自增主键，`resource_sections` 通过 `resource_id` 外键挂在同一库。按「图片/视频」和「文本」拆成两个文件会带来：

- 行 ID 在两个库各自自增，同一 ID 指向两份资源，破坏对外返回的 `id` 语义；
- `resource_sections` 与 `resources` 的级联删除、跨资源搜索、全局统计都要跨库手工拼装；
- 句柄分配器需要按类型路由到不同连接，收益却只是文件名不同。

因此「统一资源名录」本身就是一个领域，保持单库；与它相关的派生缓存（媒体摘要、视觉副本）和文本索引才拆出去。

## 迁移

启动时由 `InitArchiveDB` / `InitKnowledgeDB` 自动执行，幂等：

1. 检测旧 `knowledge.db` 中的 `video_summary`、`web_ltp_page_cache`、`file_mapping`、`painter_characters`，复制到对应领域库后删除旧表；
2. 检测旧 `archive.db` 中的 `vision_cache`，复制到 `media.db` 后删除旧表；
3. 删除前用 `VACUUM INTO` 整库备份到 `{LocalDir}/backup/database/`；备份失败则不动旧表，下次启动重试。

迁移只搬内建表；`knowledge.db` 中用户与插件自建的表原样保留。

## 路由与访问

- 月华 `knowledgeLoad` / `knowledgeSave` 的**逻辑表名不变**，由 `persistence.knowledgeBuiltinTables` 路由到实际库；未登记的表仍落 `knowledge.db`。
- `/knowledge/` 端点的 `db` 支持领域名：`knowledge`（默认）、`archive`、`media`、`web`、`text`、`character`；也仍支持按文件名访问 `database/` 下的其它库。
- LTP9 `database.*` 默认库仍是 `knowledge.db`；需要独立库时用 `database.namespace(name)`。

## 约束

1. 新增表先确定领域库并登记到 `domain_db.go` 的 schema，禁止再往 `knowledge.db` 塞内建缓存。
2. 跨库不做外键，只允许按句柄、内容哈希、URL、逻辑表键这类稳定键弱关联；删除与一致性由代码负责。
3. 领域库连接由 `domainDB` 统一懒打开；路径变化自动重开，便于测试隔离。
4. 派生数据（视觉副本、摘要缓存）丢失可重建，迁移与清理不需要保证强一致。
