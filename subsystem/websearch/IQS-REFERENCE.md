# 阿里云 IQS 参考分析

> 为联网搜索模块优化提供参考。我们模块的定位：**供智能体（LLM Planner）调用的工具**，返回文本结果给模型消费，不是给人看的前端界面。因此流式、UI、多模态等能力不在考虑范围内。

---

## 一、架构对比：我们 vs IQS

| 维度 | 我们 | IQS |
|------|------|-----|
| 搜索引擎 | 自建多引擎 HTML 抓取（Bing→百度→搜狗→DDG） | 自建语义索引 + 聚合多源（夸克/高德/飞猪/淘天） |
| 轻量搜索 | `simple`：Bing→百度→搜狗→DDG 回退，返回标题+摘要 | `LiteAdvanced`：500ms 语义检索，返回1-50条 |
| 常规搜索 | `webpage`：搜索 + HTTP抓取正文 + 关键词过滤 + LLM总结 | `Generic`：950ms，返回10条 + 可选正文 |
| 深度搜索 | `depth`：LLM拆子问题 → 并行搜索 → URL去重 → 抓取正文 → **研究校验（Gap Check）**→ 补充搜索 → 综合报告 | `Deep`：6s，**Multi-Agent 迭代式**（规划→搜索→阅读→反思→循环） |
| 相关性判断 | 关键词匹配 + 标题/摘要检查 | Embedding 粗排 + Rerank 精排（Qwen3系列模型） |
| 内容获取 | 自建 HTTP 抓取 + 无头浏览器 SPA 渲染 | 内置 ReadPage 服务（静态/动态两档） |
| 部署 | 自部署 Go 库 | 云服务 API |

## 二、值得参考的设计

### 2.1 结果 Rerank（相关性提升）

**IQS 做法**：搜索返回后，用 Rerank 模型对结果重排序，mAP 提升约 5%。

**我们现状**：`checkContentRelevance()` 是纯关键词匹配，判定逻辑：
- 标题/摘要匹配完整查询词 → 直接通过
- 正文匹配 ≥ 一半关键词 → 通过
- 官方网站 → 跳过过滤

**可优化点**：关键词匹配无法理解语义（如"苹果手机"和"iPhone"），可以引入 LLM 做轻量 Rerank：
- 不改变搜索流程，只在结果返回后让 LLM 对 top-N 结果打分排序
- 用工具模型池已有的模型，不增加额外成本
- 可以做成可配置开关（默认关闭，按需开启）

### 2.2 时间范围过滤

**IQS 做法**：`timeRange` 参数（OneDay/OneWeek/OneMonth/OneYear）+ 精确起止日期。

**我们现状**：无时间过滤能力，所有搜索结果混在一起。

**可优化点**：在 `SearchMode` 或工具参数中增加 `timeRange`，搜索引擎层面目前只有百度支持按时间排序（部分支持），但可以在结果返回后用发布时间过滤。对 Agent 来说，问"最近的新闻"时能自动过滤旧结果很有价值。

### 2.3 内容深度——正文长度

**IQS 做法**：Deep 引擎返回 `mainText` 最长 **50000 字符**，远超我们的 1500 字符。

**我们现状**：
- `webpageMaxPerPageLen = 1500`（单页截断）
- `depthMaxFetchedContentLen = 1500`（深度搜索同）

**可优化点**：1500 字符对 Agent 来说可能不够，尤其对于需要详细信息的深度搜索。可以适当提升到 3000-5000，让模型有更多上下文做判断。token 预算方面，现在 LLM 普遍支持 128K 上下文，不用太抠。

### 2.4 深度搜索的"全局 Memory"

**IQS 做法**：DeepSearch 每轮迭代后汇总已有信息，更新全局 Memory，确保推理路径不丢失。

**我们现状**（研究校验模式）：Gap Check 每轮检测信息缺口，补充搜索后将新数据追加到研究数据中，已有数据不会被覆盖或丢失。但缺少结构化的"已确认事实"清单，仅依赖原始数据追加。

**可优化点**：在 Gap Check 流程中增加一个结构化的 `confirmedFindings` 字段，不依赖原始数据追加，而是独立维护一份"已确认的事实"清单，供后续轮次直接引用和校验。

### 2.5 深度激发机制

**IQS 做法**：通过 prompt 明确告知"问题必有解"，防止 LLM 两轮无果就放弃。

**我们现状**（研究校验模式）：Gap Check 的 `checkGap()` 在 LLM 判断信息充足时自动退出循环，配合 `MaxGapRounds` 上限兜底。如果 LLM 过早判断"信息充足"，可能遗漏重要信息。

**可优化点**：在缺口检测的 prompt 中增加约束："如果信息仍不充分，即使已有部分信息，也应继续列出具体缺失的方面"，配合 `MaxGapRounds` 上限兜底。这与 Gap Check 的设计理念一致——宁可多搜一轮，也不漏信息。

## 三、不需要参考的部分（以及原因）

| IQS 能力 | 为什么不需要 |
|----------|-------------|
| 流式输出（AiSearch SSE） | Agent 工具是请求-响应模式，不需要流式 |
| 多模态搜索（搜图） | 不在当前搜索模块范围，已有独立的 VisionProvider |
| RichMainBody（OCR/ASR） | 对 Agent 文本输入场景无意义 |
| MCP/Skill 多平台接入 | 我们是 Go 库内嵌，不是独立服务 |
| 垂域查询（周边POI/医疗） | 我们有独立的天气插件等，不耦合到搜索模块 |
| 自建语义索引 | 需要大规模基础设施，我们走的是"借助现有搜索引擎"路线 |

## 四、实际优化建议（按优先级）

### 高优先级：影响搜索质量

| 优化项 | 改动量 | 效果预期 |
|--------|--------|----------|
| **LLM Rerank**：对搜索结果用 LLM 重排序 | 中（新增 rerank 函数 + 配置开关） | 相关性明显提升，尤其语义相近但关键词不同的查询 |
| **内容截断放宽**：1500 → 3000-5000 字符 | 小（改常量） | 给 Agent 更多上下文，减少"信息不够"的情况 |
| **深度激发约束**：Gap Check prompt 中防止过早退出 | 小（改 prompt 字符串） | 减少信息遗漏，提升深度搜索结果完整度 |

### 中优先级：增强搜索能力

| 优化项 | 改动量 | 效果预期 |
|--------|--------|------|
| **时间范围过滤**：工具参数 + 结果过滤 | 中（工具参数 + 过滤逻辑） | 时效性查询更精准 |
| **全局 Memory**：Gap Check 中结构化事实积累 | 中（新增字段 + 更新逻辑） | 校验轮次间信息不丢失，后续更有依据 |
| **正文 Markdown 格式**：保留原文结构 | 小（输出格式调整） | Agent 更容易解析结构化信息 |

### 低优先级：锦上添花

| 优化项 | 改动量 | 效果预期 |
|--------|--------|------|
| 行业分类优先召回 | 大（需要站点分类数据） | 垂域场景有帮助，但维护成本高 |
| 迭代式搜索模式 | 大（新增独立搜索模式） | 与 Gap Check 互补，但架构改动大 |
| 网页解析统一接口 | 中（封装已有能力） | 代码整理，不影响功能 |
